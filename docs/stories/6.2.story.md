# Story 6.2: Performance, Caching, and Query Optimization

## Status: Draft

## Story

As a player,
I want sessions, discovery, and analytics to stay fast as the community grows,
So that browsing and joining never feels slow.

## Context Source

- Source Document: docs/epics/epic-6.md (Story 6.2, Workstream WS2)
- Enhancement Type: Brownfield performance hardening
- Existing System Impact: Replaces the in-memory cache with Redis and tunes hot queries/indexes

## Acceptance Criteria

**Functional Requirements:**

1. `backend/src/services/cacheService.ts` is backed by Redis (installed `redis` dependency) with graceful in-memory fallback when Redis is unavailable
2. Discovery/session/analytics read paths cached with documented TTLs and explicit invalidation on writes
3. `backend/src/middleware/caching.ts` middleware verified and applied to hot endpoints
4. Slow Prisma queries identified and optimized; missing indexes added via a new Prisma migration

**Integration Requirements:**

5. Existing API response contracts and envelopes unchanged
6. `config/socket.ts` and analytics services continue to function when cache is cold or down
7. `cacheHealthCheck` exposed for monitoring (Story 6.3)
8. No cache dependency for correctness on mutating flows

**Quality Requirements:**

9. p95 < 200 ms and p99 < 500 ms on core session routes under load test
10. Cache hit rate > 80% on analytics/read-heavy endpoints
11. Load test script/results committed and thresholds documented
12. Cache invalidation covered by tests (no stale-read regressions)

**Non-Functional Requirements:**

13. Redis connection configured via env (`REDIS_URL`); no hardcoded hosts
14. Cache failures degrade gracefully, never 500 the request
15. Memory bounds enforced (max entry size/eviction policy)
16. No PII written to cache keys or values beyond existing exposure

## Dev Technical Guidance

### Existing System Context

`backend/src/services/cacheService.ts` currently implements an **in-memory** `Map`-based cache with TTL config (discovery 5 min, session 10 min, popular 15 min, location 30 min, stats 60 min) and a 256 MB cap, despite the `redis` package being installed. `backend/src/middleware/caching.ts` already provides `cachingMiddleware`, `cacheInvalidationMiddleware`, `cacheWarmingMiddleware`, and `cacheHealthCheck`. Prisma models are extensive; the MVP hot path is `MvpSession`/`MvpPlayer`.

### Integration Approach

Introduce a storage abstraction in `CacheService` with a Redis driver and an in-memory fallback, keeping the existing interface so callers are unchanged. Apply `cachingMiddleware` to discovery/session/analytics GETs and `cacheInvalidationMiddleware` on their writes. Profile with Prisma query logging, add indexes for the observed slow filters (e.g., session discovery by status/visibility/location), and add a load test.

### Technical Constraints

- Keep cache TTLs meaningful; misuse risks stale data after writes.
- Redis outage must not break the app.
- Index migrations must be additive and reversible.

## Risk Assessment

- **Primary Risk:** Stale cache serves incorrect session state.
- **Mitigation:** Write-through invalidation, short TTLs on mutable data, and explicit invalidation tests.
- **Rollback:** Disable the Redis driver and middleware application; fall back to in-memory/direct reads.

**Compatibility Verification:**

- [ ] No breaking changes to existing APIs
- [ ] Database changes are additive only
- [ ] UI changes follow existing design patterns
- [ ] Performance impact is negligible
