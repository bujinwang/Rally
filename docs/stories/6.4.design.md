## 1. Implementation approach & decisions

### D1 — Redis adapter with local fallback (firm)

Add `@socket.io/redis-adapter` for multi-instance scaling. When `REDIS_URL` is set, create a Redis pub/sub connection pair and attach the adapter. When absent, use the built-in in-memory adapter (default, no code change needed). This keeps local dev simple while enabling production scaling.

### D2 — JWT auth in socket handshake (firm)

Replace event-based `auth:identify` with **handshake authentication**:
- Client sends `auth: { token: 'Bearer <jwt>' }` in socket handshake options.
- Server verifies JWT during `io.use()` middleware.
- If valid: attach `user` to `socket.data` and join `user-${userId}` room.
- If invalid token: reject connection with `Authentication error`.
- If no token: allow as **guest** socket; attach `deviceId` from handshake query if provided.

This aligns with Story 6.1's auth model and prevents unauthenticated sockets from joining rooms.

### D3 — Room isolation (firm)

- Session rooms: `session:${shareCode}` (colon namespacing, consistent with cache keys)
- Tournament rooms: `tournament:${tournamentId}`
- User rooms: `user:${userId}`
- Discovery rooms: `discovery:${lat}:${lng}:${radius}` (unchanged pattern)
- A socket can only join a session room if the user is a participant (verified via DB) OR if it's a guest with the correct `deviceId`.

### D4 — Event-driven tournament analytics (firm)

Replace the placeholder with a `TournamentAnalyticsEmitter` service that:
- Listens for tournament lifecycle events (match complete, bracket update)
- Emits `tournament:update` to the tournament room after DB persist
- Emits `tournament:leaderboard` when standings change
- Never emits unpersisted state as authoritative

### D5 — Reconnect and missed-event recovery (firm)

Use Socket.io's built-in `reconnect` with custom `socket.data.lastEventId` tracking:
- Each emitted event carries an `eventId` (monotonic counter or timestamp).
- On reconnect, client sends `lastEventId` in handshake.
- Server checks if events were missed and either re-emits or tells client to refetch.
- For simplicity: if missed events > 10, tell client to refetch full state instead of replaying.

### D6 — Frontend compatibility (firm)

Keep ALL existing event names and payload shapes stable. Add new events additively. The frontend `socketService.ts` changes are minimal:
- Add `auth.token` to connection options.
- Add reconnect handler with `lastEventId`.
- Add polling fallback when socket fails to connect after 3 retries.

## 4. Shared conventions

- Event names: lowercase with colons (`session:update`, `tournament:leaderboard`).
- Room names: kebab-case with colons (`session:ABC123`).
- Auth: JWT in handshake `auth.token`, guest with `auth.deviceId`.
- Adapter: Redis when `REDIS_URL` set; memory otherwise.
- Never emit unpersisted state.

## 6. Implementation notes / deviations

Recorded after implementation. Items marked **FIX** were defects found and
corrected during the build; items marked **DEV** are deliberate deviations from
the original design text.

| # | Type | Item | Resolution |
|---|------|------|------------|
| FIX-1 | P0 | `app.set('io', io)` was never called in `server.ts`, so the five `req.app.get('io')` emission points in `routes/mvpSessions.ts` silently no-op'd — clients never saw live rotation/score/status updates (AC 4 broken end-to-end). | Added `app.set('io', io)` right after `io` is constructed; verified causally (route POST now delivers to a joined room). |
| FIX-2 | P0 | `auth:identify` trusted a client-supplied `userId` (`socket.data.user?.id \|\| data.userId`), letting a **guest** join any authenticated user's private `user:*` room (AC 14 leak). | The verified handshake identity now always wins; guests are rejected with `auth:error` and never join a user room. |
| FIX-3 | P1 | `setTournamentIo` was removed in favour of the shared registry, but `config/socket.ts` still imported it. | Consolidated all emitters onto `socket/ioRegistry.ts` (`setIo`/`getIo`). |
| FIX-4 | P1 | Design referenced a `TournamentStanding` model and `MvpMatch.player1Score`; neither exists in `schema.prisma`. | Standings are derived from `TournamentPlayer`; scores are read from `MvpGame` (`team1FinalScore`/`team2FinalScore`). |
| DEV-1 | — | Design named `env.socket.adapter` but omitted it from `config/env.ts` / `.env.example`. | Added the `socket` block (adapter, redisUrl, patienceMs, maxReplayEvents, eventBufferSize) + `.env.example` docs. |
| DEV-2 | — | Design had no event-sequencing mechanism beyond "monotonic counter or timestamp" (D5). | Implemented a bounded per-room replay ring in `ioRegistry.ts` with `nextEventId()`, `emitToRoom()`, `resolveMissedEvents()`; replay when the gap ≤ `SOCKET_MAX_REPLAY_EVENTS`, otherwise `refetch`. |
| DEV-3 | — | Design named `events/sessionEvents.ts` but did not define the emitter surface. | Exposed `emitSessionSnapshot`, `emitPlayerStatusChanged` (rotation), `emitScoreUpdated` (scoring), `emitPlayerJoined`/`emitPlayerLeft`, `invalidateSessionCache`. |
| DEV-4 | — | Adapter shutdown was not wired. | `detachAdapter()` added and called from the existing SIGTERM/SIGINT handler so the pub/sub clients close cleanly (mirrors the Story 6.2 cache shutdown). |
| DEV-5 | — | Frontend D6: reconnect + polling fallback. | `socketService.ts` tracks `lastEventId` per room, re-subscribes on `connect`, sends `sync:resume`, and degrades to a 15s polling heartbeat after `maxReconnectAttempts`. |
| FIX-5 | P0 | `join-session` joined rooms unconditionally (no DB authorization), and `sync:resume` replayed any client-named room's buffer — both violated D3/AC 14 (any socket could read any session's snapshot + events). | `join-session` now authorizes the handshake identity (participant via `MvpPlayer` / owner via `MvpSession.ownerUserId\|ownerDeviceId`) in a single `findUnique` before joining; unauthorized sockets get `auth:error` and join nothing. `sync:resume` drops any room where `!socket.rooms.has(room)`. `join-tournament` authorizes via `tournament.visibility` (public → open) + `TournamentPlayer.deviceId` (private → participant only), fails closed. |
| FIX-6 | P1 | Redis adapter `await Promise.all([connect, connect])` never settled against an unreachable Redis (node-redis retries forever); clients leaked and `detachAdapter()` could never close them. | Bounded with `Promise.race` vs `env.redis.connectTimeoutMs` + `reconnectStrategy: false`; `redisClients` assigned before connect so `detachAdapter()` always closes them; `hasRedisAdapter()` now reflects actual attachment (separate `redisAdapterAttached` flag). |
| FIX-7 | P1 | Tournament emitters (`emitMatchComplete`/`emitBracketUpdate`/`emitLeaderboardUpdate`) were dead code — never called on the real write path (AC 3 half-delivered). | `tournamentBracketService.updateMatchResult()` now calls `emitMatchComplete()` + `emitLeaderboardUpdate()` after the result is persisted, wrapped in try/catch so real-time failures never break the business path. `join-tournament` now serves the bracket via the shared `loadBracket()` helper (one source of truth). |

### Second-round defects (found after the first QA pass)

The Defect-1 fix (FIX-5) was validated only by unit tests that **mock the
handshake and pre-populate `socket.data.deviceId`** — so the suite was green
while the real client, which sent no identity at all, could no longer join. A
live probe with a realistically-shaped socket was required to surface these.

| # | Sev | Defect | Fix |
|---|-----|--------|-----|
| FIX-8 | **P0** | **Guest socket regression.** FIX-5 requires a verified `userId` *or* a `deviceId`; the frontend sent **neither** — the handshake was `auth:{token:undefined}` and `joinSession(shareCode, deviceId)` accepted a `deviceId` then emitted a **bare string, discarding it**. Guests could no longer join their own sessions (regression of the Story 6.1 guest-join feature). | Handshake now sends `deviceId` from `DeviceService.getDeviceId()`; `joinSession` is async and emits `{ shareCode, deviceId }`; `resumeRooms` re-joins through the same authenticated path. `deviceService` does not import `socketService`, so there is no circular import. |
| FIX-9 | P1 | **Every authoritative event delivered twice.** `emitSessionSnapshot` mirrored the payload into both `session:${code}` and the legacy `session-${code}`, and a joining client is placed in **both** rooms — so clients received two copies, violating AC 8. | The legacy kebab-room mirror is removed; the snapshot goes to the canonical colon room exactly once. Safe because the legacy route layer emits **only** to the kebab room (19 sites in `routes/mvpSessions.ts`, none to a colon room), so its behaviour is unchanged. `events.test.ts` now asserts exactly-once delivery **and** guards that the kebab room never receives it. |
| FIX-10 | P2 | Frontend reconnect replay was inert — `joinedRooms` was declared and iterated by `resumeRooms()` but never populated, so `resumeRooms()` early-returned and `sync:resume` was never sent (AC 8/11 dead). | `joinSession` adds / `leaveSession` deletes, plus `lastEventIds` cleanup on leave; `joinTournament` / `leaveTournament` restored. Behaviourally proven with a mock-socket harness (7/7). |
