# Story 6.9 — Phase 2: Release Ops Workstream

**Status: Not started. Not executable on this machine. Needs an owner with store access.**

This document is the standalone workstream for the acceptance criteria that **moved out of Story 6.9**
when it was re-scoped to Phase 1 (decision Q3 — see `6.9.design.md` §7 and `6.9.story.md`). It exists
so those commitments stay **visible and owned** rather than silently dropped, and so that whoever
picks it up can see what each one actually requires.

**Read this as a statement of what cannot be done here, not as a plan that pretends it can.** The
machine this work was designed on has no Expo/EAS account, no App Store Connect access, no Play
Console access, and no production telemetry. Every AC below is therefore either **blocked** or
**not started**, and none of them can be "completed" by an agent in this environment. Producing
artefacts that *look* complete — a stub `eas.json`, a filled-in privacy manifest with no basis — would
be worse than leaving them open.

## What an owner needs

| Capability | Used by |
|---|---|
| Expo account + EAS CLI, project linked to an Expo org | AC 1, 8, 15 |
| Apple Developer Program membership + App Store Connect access | AC 4, 13 |
| Google Play Console access | AC 4, 13 |
| Production API environment + Story 6.3 observability credentials | AC 8, 9 |
| Production telemetry / analytics (crash reporting, opt-in funnel) | AC 9, 10 |
| A CI host with secret storage (see AC 14 — currently **none**) | AC 14 |

---

## AC 1 — EAS production builds + documented, repeatable release pipeline

- **What it requires:** `eas.json` with `build`/`submit` profiles (development / preview / production),
  `app.json`/`app.config.*` production config (bundle ids, versioning, credentials), and a
  `docs/release-process.md` describing the exact repeatable steps.
- **Access:** Expo account + EAS, plus iOS/Android signing credentials.
- **Status:** **Not started** — no `eas.json`, no `docs/release-process.md` exist.
- **Owner must:** link the project to an Expo org, define the three profiles, configure production
  build credentials, run a production build on both platforms, and document the steps so a second
  person can repeat them without guesswork.

## AC 4 — App Store and Play Store approval

- **What it requires:** submitted, review-ready builds; store listings; screenshots; privacy answers;
  a scope freeze during review.
- **Access:** App Store Connect + Google Play Console (Apple Developer Program / Play Console account).
- **Status:** **Not started.**
- **Owner must:** submit via EAS submit, respond to review feedback, and hold the release until
  approval. This cannot begin until AC 1 produces a build.

## AC 8 (release-build portion) — Release builds point at production API + observability

- **What it requires:** production environment configuration baked into release builds, plus wiring the
  Story 6.3 observability pieces (`metricsRegistry`, `correlationId`) into the release path.
- **Access:** production API environment + Story 6.3 observability credentials.
- **Status:** **Partly addressable in Phase 1** (pointing release config at the production API and
  wiring the 6.3 hooks); the **actual production release-build** portion is **not started** here.
- **Owner must:** provision the production API URL/keys for release builds and confirm metrics/
  correlation are emitted from a production build.
- **Note:** the *addressable part* is retained in Phase 1 (`6.9.story.md` task "T8b").

## AC 9 — Crash-free sessions > 99.5%

- **What it requires:** production crash telemetry (e.g. Sentry/Crashlytics/Expo), a defined
  "crash-free sessions" metric, and enough live traffic to measure it.
- **Access:** production telemetry service + release builds in users' hands.
- **Status:** **Not started / not measurable here.** No production telemetry exists on this machine.
- **Owner must:** instrument the app, ship to production, and report the metric over a representative
  window. Depends on AC 1 + AC 4.

## AC 10 — Push opt-in > 60%

- **What it requires:** production analytics for the push-permission funnel (prompt shown → granted),
  and live users.
- **Access:** production analytics.
- **Status:** **Not started / not measurable here.**
- **Owner must:** instrument the opt-in funnel, ship, and measure. Depends on AC 1 + AC 4.

## AC 12 (staged-rollout portion) — Staged rollout mechanics

- **What it requires:** a staged/phased rollout mechanism (e.g. Play staged rollout %, App Store phased
  release, or a feature-flag/percentage gate) **and** a documented rollback procedure.
- **Access:** Play Console staged rollout controls / App Store phased release; release pipeline (AC 1).
- **Status:** **Partial** — the **rollback documentation already exists** (`docs/rollback-procedures.md`,
  320 lines) and stays in Phase 1. The **staged-rollout mechanism itself is not started** and moves here.
- **Owner must:** configure a staged rollout, define halt criteria, and reconcile the existing rollback
  doc with the store mechanisms actually used.

## AC 13 — Store policy compliance (privacy manifest, data-safety)

- **What it requires:** iOS `PrivacyInfo.xcprivacy` privacy manifest, App Store privacy nutrition
  labels, and Google Play Data Safety declarations — each must accurately reflect what the app collects.
- **Access:** App Store Connect + Play Console; and a truthful data-collection inventory from the code.
- **Status:** **Not started.**
- **Owner must:** inventory data collection (incl. push tokens, device ids, analytics), fill the store
  forms to match, and add the privacy manifest to the build. Depends on AC 1.

## AC 14 — Secrets/credentials in CI, not the repo — **BLOCKED**

- **What it requires:** a CI workflow that injects secrets from a secret store at build time, and no
  credentials committed to the repo.
- **Access:** a working CI host with secret storage.
- **Status:** **BLOCKED — there is no CI host.** `.github/workflows/ci.yml` exists on disk but is
  **explicitly gitignored** (`.gitignore:20`); `git check-ignore -v` confirms it, and
  `git ls-files .github/workflows/` lists only `codeql.yml` and `release.yml`. **No CI runs on push at
  all**, so AC 14 has nowhere to run.
- **Owner must (in order):** (1) decide whether to un-ignore and track `ci.yml` — a **repo-hygiene
  decision**, not a 6.9 code change; (2) provision secrets in the CI host; (3) reference them from the
  workflow without committing values. **This AC cannot progress until step 1 is decided.**

## AC 15 — Build reproducibility documented

- **What it requires:** a documented, deterministic build (pinned toolchain/dependency versions,
  documented env, repeatable steps).
- **Access:** the release pipeline (AC 1).
- **Status:** **Not started.**
- **Owner must:** pin versions, document the exact build commands/environment, and verify two
  independent builds from the same commit produce equivalent artefacts. Depends on AC 1.

---

## Suggested order

1. **AC 14 step 1** (un-ignore/track `ci.yml`) — unblocks CI and is a prerequisite for reproducible,
   secret-safe builds.
2. **AC 1** (EAS profiles + release process doc) — unblocks everything else.
3. **AC 15** (reproducibility doc) — cheap once AC 1 exists.
4. **AC 13** (privacy manifest / data-safety) — required before submission.
5. **AC 4** (store submission) — depends on AC 1 + AC 13.
6. **AC 12** (staged rollout) — configures how AC 4's release is released.
7. **AC 8** (production wiring) — ships with the release.
8. **AC 9 / AC 10** (measurement) — only meaningful after real users are on the release.

## Explicitly out of scope here

Phase 1 (this story, `6.9.story.md`) retains and owns: AC **2, 3, 5, 6, 7, 11, 16**, plus the
addressable parts of AC **8** (production-API/observability wiring) and AC **12** (rollback doc).
Phase 2 does not re-open those.
