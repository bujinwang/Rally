# Story 6.5: Offline Sync and Conflict Resolution

## Status: Draft

## Story

As a player at a venue with poor connectivity,
I want my actions queued and reconciled when I'm back online,
So that no scores or session data are lost.

## Context Source

- Source Document: docs/epics/epic-6.md (Story 6.5, Workstream WS5)
- Enhancement Type: Brownfield offline hardening and verification
- Existing System Impact: Hardens existing `syncManager` queue and adds documented reconciliation/export guarantees

## Acceptance Criteria

**Functional Requirements:**

1. `frontend/Rally/src/services/syncManager.ts` queue hardened with ordering, retry, and exponential backoff
2. Server-authoritative conflict resolution with last-writer-wins and explicit conflict surfacing to the user
3. Offline reads served from persisted state (`AsyncStorage`/`redux-persist`); writes queued
4. Data export/backup and restore guarantees implemented and documented

**Integration Requirements:**

5. Sync uses the auth identity (Story 6.1) and real-time transport (Story 6.4) when available
6. Existing queue/hooks API preserved for callers
7. Conflict outcomes reflected in the same UI state model as online updates
8. No silent data discard on schema version changes

**Quality Requirements:**

9. Conflict auto-resolution > 95%; 100% of unresolved conflicts surfaced
10. Zero data loss across offline→online reconciliation in UAT and chaos tests
11. Deterministic ordering tests for queued mutations
12. Documented, testable export/restore path

**Non-Functional Requirements:**

13. Queue persists across app restarts
14. Bounded queue size with eviction policy documented (no unbounded growth)
15. Offline UX states (queued, syncing, conflict, failed) clear and localized
16. Sensitive data in the queue handled per privacy rules

## Dev Technical Guidance

### Existing System Context

`frontend/Rally/src/services/syncManager.ts` implements a singleton `SyncManager` using `@react-native-community/netinfo`, listens for network state, queues operations, and throws when offline. `frontend/Rally/src/services/storageService.ts` and `store/index.ts` use `AsyncStorage`/`redux-persist`. There is no tested conflict-resolution or export/restore guarantee today.

### Integration Approach

Define a canonical operation record (id, entity, op, payload, version, timestamp) with a monotonic ordering. On reconnect, replay in order with server-side version checks; on conflict, apply last-writer-wins and emit a conflict record for UI surfacing. Provide an export (JSON) and restore path, with schema-version handling.

### Technical Constraints

- Reuse the existing `SyncManager` interface; do not fork a second sync system.
- Server remains authoritative; client timestamps are advisory.
- Export must not leak another user's data.

## Testing

### Validation Steps

1. Go offline, perform mutations, restore network, verify reconciliation
2. Simulate concurrent edits to force a conflict and verify resolution + surfacing
3. Restart the app with a pending queue and verify persistence
4. Export, wipe, restore, and verify data
5. Run `npm run lint` and `npm test` in `frontend/Rally`

### Test Scenarios

- Ordered replay of queued mutations
- Conflict auto-resolution and surfacing
- App restart with pending queue
- Corrupt/oversized queue handling
- Export/restore round-trip

## Risk Assessment

- **Primary Risk:** Silent loss or corruption of scores during reconciliation.
- **Mitigation:** Persistent ordered queue, server-authoritative version checks, explicit conflict surfacing, and chaos testing.
- **Rollback:** Disable replay (queue-only mode) while preserving local data for manual recovery.

- [ ] No breaking changes to existing APIs
