## 1. What changed

Story 5.5 shipped `backend/src/services/predictiveAnalyticsService.ts` with
**fabricated** outputs. Four accuracy constants were hardcoded and presented as
measured model performance:

| Family | Old hardcoded "accuracy" | Old implementation |
|---|---|---|
| demand | `0.78` | `mockLinearRegression` → returned the target **mean** |
| churn | `0.72` | `mockLogisticRegression` → returned a constant **`0.5`** |
| seasonal | `0.80` | `mockLinearRegression` on `$queryRaw` output |
| optimization | `0.85` | `mockLinearProgramming` → **`Math.random()`** |

Additional defects found in recon: the service instantiated its own
`new PrismaClient()` at module scope, queried `prisma.session` (mapped to the
**empty** `sessions` table rather than `mvp_sessions`), capped demand history at
`take: 365`, and its `explanation` strings claimed methods that were never
implemented (e.g. "ARIMA forecasting").

Story 6.6 replaces all of it with real estimators, a computed held-out
evaluation, and an honesty-labelled fallback path.

## 2. Evaluation protocol

### 2.1 Dataset sources

| Family | Source | Grouping |
|---|---|---|
| demand | `mvp_sessions` where `status = COMPLETED` | per `location` |
| seasonal | `mvp_sessions` | by month bucket |
| churn | `mvp_sessions ⋈ mvp_players` (participation history) | per **identity** |
| optimization | `courts` + `court_bookings` | per venue/date |

All-time history; the old `take: 365` cap is removed.

### 2.2 Churn identity unit (the hardest modelling decision)

`MvpPlayer.sessionId` is **required**, so a row is a *per-session participation
record*, not a person. "Churned player" was therefore undefined in the original
design. Resolution:

- **Identity = `COALESCE(userId, deviceId)`** — dedupe participation rows to one
  row per identity. `resolveIdentity()` implements `u:${userId}` with fallback to
  `d:${deviceId}`.
- **`status = LEFT` is NOT a churn signal.** It is set only by
  `DELETE /:shareCode/leave`, i.e. going home after one session, and would have
  mislabelled routine departures as churn.
- **Label = `1` iff `(LAST_OBSERVED_DATE − lastParticipation) > 60 d`**, where
  `LAST_OBSERVED_DATE = max(scheduledAt)` over the filtered dataset.
  60 d ≈ 4× a weekly-player cadence.

**Why a closed window matters:** using `Date.now()` would make labels
non-reproducible and introduce lookahead bias — a label could change with wall
time even though the data did not. Anchoring to `max(scheduledAt)` makes every
evaluation reproducible.

### 2.3 Splits

- **Temporal 80/20** for demand (train on earlier, hold out the latest 20%).
- **Stratified** for churn (both classes present in the holdout).
- **Tail holdout** for seasonal (trailing 4 month buckets).
- All splits are **seeded and deterministic** — the same seed yields an identical
  split, verified in `evaluation.test.ts`.

### 2.4 Metrics

| Metric | Use |
|---|---|
| `mape` / `regressionEfficiency` | demand, seasonal |
| `rocAuc` / `classificationAccuracy` | churn |
| `featureContributions` | explainability for all linear families (AC 12) |

Metrics are stored 0–1 (`MAPE` as a ratio) in `PredictionModel.metrics`.

### 2.5 Activation gate

A trained model is persisted, but only **activated** if **all** hold:

- `modelKind = 'measured'`, **and**
- computed `accuracy ≥ 0.75` (`ACTIVATION_MIN_ACCURACY`), **and**
- `trainingDataSize ≥ minSamples` for its type.

Per-type minimum-sample thresholds, all enforced in code:

| Type | Gate |
|---|---|
| demand | ≥ 40 completed sessions for the location **and** ≥ 8 holdout rows |
| churn | ≥ 60 distinct identities **and** ≥ 10 positives, ≥ 3 observations each |
| seasonal | ≥ 12 **populated** month buckets (each with ≥ 1 completed session) |

Only one active model per type (transactional invariant); any prior version can
be reactivated by operator **rollback**, so a bad deploy is always reversible.

## 3. Estimators — verified on synthetic ground truth

Because the live dataset cannot train anything (see §5), the estimator maths is
verified against **planted** relationships where the correct answer is known:

| Claim | Method | Observed |
|---|---|---|
| Ridge recovers a linear relation | planted `y = 2x₁ − x₂ + 3` | coefficients `[2.0000000000, −1.0000000000]`, intercept `3.0000000003` |
| Logistic separates separable data | 1-D separable, `epochs 2000, lr 0.1` | AUC **1.000**, accuracy **1.000** |
| Logistic learns a 2-feature boundary | planted `2a + 1.5b + 0.3 > 0` | AUC **0.99991** |
| Seasonal recovers trend + index | planted slope `0.5`, peak month 7 | slope **0.511**, peak month **7** |
| Determinism | same input twice | byte-identical output |

Linear algebra uses Gaussian elimination with partial pivoting; singular /
near-singular systems are regularised (a tiny ridge is always applied) rather
than throwing.

**Crucially: synthetic data is used only to prove the estimator maths. No test
writes a `modelKind = 'measured'` row, and no field accuracy is ever claimed
from synthetic data.** That is enforced by assertions in
`predictiveAnalyticsService.test.ts`.

## 4. Anonymization & privacy (AC 13)

- **Feature rows are all-numeric.** The identity key and the raw `playerId`,
  `name`, `deviceId`, `userId`, `email` are dropped at extraction — identity is
  used only to *group*, never emitted.
- **Location is hashed** (`anonymizeLocation` → SHA-1), and stored inputs use a
  digest (`playerRef`, `venueRef`) rather than raw ids.
- **Metric labels have bounded cardinality.** `type` and `modelKind` are closed
  enums; no ids or free text ever become a Prometheus label.
- **Guard test:** `features.anonymization.test.ts` asserts no key matching
  `/name|deviceId|userId|email|playerId/i` appears in feature rows or the
  dataset descriptor, including **nested** keys and **values**. The legitimate
  structural key `FeatureSpec.names` is explicitly allowlisted rather than
  weakening the pattern — so `playerName`, `userName`, `deviceIdSuffix`,
  `userIds`, `emails` all remain caught.

## 5. AC 9 honesty position — the numeric target is NOT met here

**AC 9 requires "measured accuracy > 75% on held-out data for churn and demand".
This is not achieved in this environment, and it is deliberately not faked.**

Live dataset measured directly from `badminton_group`:

| Table | Count |
|---|---|
| `mvp_sessions` | 7 |
| `mvp_sessions` where `COMPLETED` | **2** |
| `mvp_players` (participation rows) | 6 |
| distinct identities after `COALESCE(userId, deviceId)` | **≈ 1–2** |
| `users` | **0** |
| `analytics_events` | 0 |

Every gate in §2.5 fails by construction: demand 2 < 40, churn ~1–2 < 60,
seasonal 2 populated buckets < 12.

With zero labelled examples you cannot honestly **train**, and with zero held-out
rows you cannot honestly **evaluate**. Reporting "> 75%" from this data would be
exactly the fabrication this story exists to eliminate.

**What is delivered instead** — the machinery that meets AC 9 the moment real
data exists:

1. Real estimators, correct on real data (verified on synthetic ground truth, §3).
2. A documented, code-enforced minimum-sample threshold that **gates activation**.
3. A **computed** (never constant) held-out evaluation stored on
   `PredictionModel.accuracy`.
4. A labelled **fallback** path used whenever data is insufficient.

**Observable behaviour today:** every prediction family returns
`modelKind: 'fallback'` (demand, churn, seasonal) or `'heuristic'`
(optimization), with `accuracy: null` and a non-empty
`fallbackReason: 'insufficient-samples'`. Verified live: no response contains
`0.78`, `0.72`, `0.80` or `0.85` anywhere, and zero `modelKind = 'measured'`
rows exist.

**Explicitly refused:** generating synthetic data and reporting it as measured
accuracy.

## 6. Bias & fairness (AC 14)

- **No protected attributes are features.** Features are behavioural and
  temporal only (day-of-week, month, capacity, recency, tenure, cadence). Name,
  contact details, and any demographic field are neither collected nor derived.
- **Identity fragmentation is the known fairness risk, and it is disclosed.**
  With `users = 0`, identity collapses to `deviceId` — a browser/IP/user-agent
  fingerprint that **changes across browsers, devices and networks**. One human
  may therefore appear as two identities. Consequences:
  - churn risk may be **understated** for a person who switched device;
  - affected users skew toward multi-device / mobile-network users.
  This is a product-level limitation, not a modelling bug, and is the residual
  open decision (options: device-only; prefer `userId` with device fallback
  — implemented; or merge-on-signup backfill once `users > 0`).
- **Small-sample bias is handled structurally:** the gate refuses to train at
  all below threshold, so no model is fitted on a group too small to be
  representative.
- **Retention advice is deterministic and content-only** — a fixed advice list
  keyed on a threshold, with no PII and no per-user profiling beyond the
  probability itself.

## 7. Bounded compute & cost (AC 15, AC 11)

- **No new dependencies.** Estimators are pure TypeScript (ridge via normal
  equations, logistic via full-batch gradient descent with L2 and early stop),
  so there is no native/GPU runtime cost.
- **Training is bounded by construction:** the gate caps what can be trained,
  and the retrain job isolates each type so one failure cannot cascade.
- **Serving is O(features)** — a dot product plus a contribution breakdown. No
  inference server, no per-request training.
- **Retrain cadence:** a single 24 h `setInterval` plus one deferred startup run,
  both `unref()`'d, so the timer never holds the process open.
- **Structural position on AC 11 (p95 < 5 s):** the serving path performs one
  indexed lookup plus a dot product, and GETs are served through the existing
  analytics cache (TTL 300 s), so a cache HIT is served without touching the
  model at all. **Not load-tested** — no production-scale dataset exists here, so
  this is a bounded-compute argument, not a measurement.

## 8. Backup & recovery (AC 16)

- **Models are versioned rows, never files.** `PredictionModel` holds
  `parameters` (coefficients + intercept), `hyperparameters`, `featureNames` and
  `metrics`, all in Postgres — so model recovery is ordinary database recovery.
- **`prediction_models` is unique on `(type, version)`** so `demand v1.0` and
  `churn v1.0` coexist. (The old global `version @unique` made this impossible
  and was dropped by migration `20260914000000_story_6_6_prediction_model_version`.)
- **Rollback is a first-class operation:** `POST /predictions/rollback` restores
  a prior version, and `rollback` may activate any prior existing version
  *including one below the 0.75 gate* — deliberately, so a bad deploy is always
  reversible without a code change.
- **Nothing is destroyed on retrain.** A new version is inserted; the previous
  one is deactivated, not deleted. Only one row per type is `isActive`.
- **`PredictionResult` cascades on model delete** (`onDelete: Cascade`), so
  removing a model row cannot orphan results.
- **Failure isolation:** the retrain job wraps every run in try/catch and never
  throws, so a training failure cannot take down the scheduler or the process.
- **Recovery procedure:** re-point the active version via rollback, or let the
  next 24 h run retrain. Because the fallback path is always available, a missing
  or failed model **degrades to a labelled fallback rather than an error** — the
  prediction surface never returns a fabricated number.
