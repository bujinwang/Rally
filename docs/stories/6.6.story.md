# Story 6.6: Real Predictive Intelligence

## Status: Draft

## Story

As a platform administrator,
I want predictions from a real, measured model,
So that demand and churn decisions rest on honest accuracy rather than mock constants.

## Context Source

- Source Document: docs/epics/epic-6.md (Story 6.6, Workstream WS6); supersedes the mock implementation in Story 5.5
- Enhancement Type: Brownfield replacement of mock ML with a real, measured model
- Existing System Impact: Replaces mock outputs in `predictiveAnalyticsService.ts`; uses existing `PredictionModel`/`PredictionResult`

## Acceptance Criteria

**Functional Requirements:**

1. `backend/src/services/predictiveAnalyticsService.ts` mock outputs (`0.5` churn, fixed `[0.2]` historical churn rate, `accuracy: 0.72`) replaced with real models
2. `PredictionModel` and `PredictionResult` in `backend/prisma/schema.prisma` used for versions, accuracy, and results
3. Demand forecasting, churn prediction, and seasonal analysis produce data-derived outputs
4. Admin-facing prediction surface continues to serve from the existing analytics API

**Integration Requirements:**

5. Training consumes existing analytics data (`AnalyticsEvent`, session/player history) without breaking the analytics pipeline
6. Model versioning: active model selection and rollback supported
7. Prediction endpoints integrate with cache (Story 6.2) and monitoring (Story 6.3)
8. The prior heuristic remains available explicitly labeled as **fallback**, never reported as measured accuracy

**Quality Requirements:**

9. Measured accuracy > 75% on held-out data for churn and demand; accuracy is computed, not hardcoded
10. Retraining pipeline completes within 24 hours
11. Prediction response p95 < 5 s
12. Explainability available for each prediction (feature contributions)

**Non-Functional Requirements:**

13. Training on anonymized data only; privacy-reviewed
14. Bias/fairness checks documented
15. Cost-effective and bounded compute for training/serving
16. Model backup and recovery procedure documented

## Dev Technical Guidance

### Existing System Context

Story 5.5 is marked Done with an explicit caveat: `predictiveAnalyticsService.ts` returns `0.5` churn probability, a fixed `[0.2]` historical churn rate, and `accuracy: 0.72`. `PredictionModel`/`PredictionResult` models exist in Prisma. Note: the Dev Notes' `backend/src/routes/predictions.ts` does **not** exist; prediction data is served through the existing analytics surface (`routes/analytics.ts`, `routes/sessionInsights.ts`).

### Integration Approach

Implement real estimators (e.g., regression/time-series for demand, logistic/GBM for churn) over features derived from `AnalyticsEvent` and session/player history. Persist each trained model version with its measured metrics; activate the best model; expose predictions and feature contributions. Compute accuracy on a held-out split and store it on the model record.

### Technical Constraints

- Do not misrepresent heuristic output as a measured model.
- Keep the analytics response envelope stable for the frontend.
- Guard against sparse-data overfitting; require minimum sample thresholds before activating a model.

## Testing

### Validation Steps

1. Train on historical data; verify measured accuracy > 75% on held-out split
2. Verify stored accuracy matches the evaluation, not a constant
3. Time a full retraining run (< 24 h) and a prediction call (< 5 s)
4. Request a prediction and verify feature contributions are present
5. Run `npm run typecheck` and `npm test` in `backend`

### Test Scenarios

- Model training and evaluation
- Model activation and rollback
- Sparse-data minimum-threshold behavior
- Fallback labeling
- Privacy/anonymization checks

## Risk Assessment

- **Primary Risk:** Sparse data yields a real model still below target, repeating 5.5's overclaiming.
- **Mitigation:** Report measured accuracy, gate activation on > 75%, require minimum sample thresholds, and label fallback honestly.
- **Rollback:** Switch active model to the previous version or the clearly-labeled fallback.

**Compatibility Verification:**

- [ ] No breaking changes to existing APIs
- [ ] Database changes are additive only
- [ ] UI changes follow existing design patterns
- [ ] Performance impact is negligible
