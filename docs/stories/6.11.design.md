## 1. The defect, restated

Three pieces of code were written to work together and none of them were connected.

| Piece | Evidence | State |
|---|---|---|
| `frontend/Rally/src/components/TournamentAnalyticsScreen.tsx` | `grep -rn TournamentAnalyticsScreen src App.tsx` → **0 hits**; absent from `components/index.ts`; in no navigator | orphaned UI |
| `backend/src/routes/tournament-analytics.ts` | `grep -rn tournament-analytics routes/index.ts server.ts` → **0 hits** | never mounted |
| `TournamentAnalyticsService` | `calculateParticipationMetrics` + `calculateBracketEfficiency` + `trackPlayerRankingChanges` | returns all 8 `AnalyticsData` fields |
| what the screen calls | `tournamentApi.getTournamentStats` → `/tournaments/:id/stats` | 6 fields, **2 of 8** overlap |

So `6.10.design.md` §3's "shape mismatch" is a symptom: the screen was written against an
`/analytics` contract that was never wired up, and the endpoint that satisfies it has been
unreachable since the day it was written.

## 3. A second, latent bug found while designing the access model

The original route guarded with `authenticateToken` + `requireRole(['ORGANIZER','ADMIN'])` and then
checked ownership as:

```ts
{ organizer: (req as AuthRequest).user?.name || 'Unknown' }
```

**`req.user.name` does not exist.** Both `authenticateToken` and `optionalAuth` select only
`{ id, email, role }` from `prisma.user`, and the middleware's own `AuthRequest` interface declares
`user?: { id; email; role }` — no `name`.

So the predicate always evaluated to `{ organizer: 'Unknown' }` and **could never match**. Two
consequences:

1. The "organizer reads their own private tournament" path was **dead** — the route only ever
   served PUBLIC tournaments.
2. It type-checked anyway, because the route file declares its **own** local `AuthRequest` with
   `user?: { id; name?; email?; role }` — a shape that is never populated. **A type that describes a
   world the middleware does not create.**

### The correct authorization already exists

`prisma/schema.prisma` says so explicitly, next to the columns:

> `organizer` above is free text and **MUST NOT be used for authorization** (design §0 finding 13).
> These nullable columns carry the resolvable identity that `requireTournamentOrganizer` matches
> against: a verified JWT `userId` first, else a `deviceId`.

So the fix uses **`organizerUserId` / `organizerDeviceId`** with `resolveIdentity(req)` — Story 6.7's
machinery — not the free-text `organizer` string.

`requireTournamentOrganizer` itself is not reusable here: it **fails closed on anonymous callers**
(403), which is right for a mutation but wrong for a read of a PUBLIC tournament.

## 4. Design

### 4.1 Backend — `GET /api/v1/tournaments/:id/analytics`

```
optionalAuth  →  handler
```

- **`optionalAuth`** (Story 6.1), not `authenticateToken` + `requireRole`: the app is device-first,
  and a read of a PUBLIC tournament should not require a JWT. An invalid token still 401s rather
  than silently downgrading.
- Handler logic:
  1. Load `{ visibility, organizerUserId, organizerDeviceId }` for the id.
  2. Not found → `404` envelope, code `TOURNAMENT_NOT_FOUND`.
  3. `visibility === 'PUBLIC'` → allow.
  4. Otherwise compute the identity via `resolveIdentity(req)` and allow **only** the organizer:
     JWT → `identity.userId === organizerUserId`; device → `identity.deviceId === organizerDeviceId`;
     anonymous → deny.
  5. Denied → `404` (not 403), matching the original's "not found **or** access denied" so a private
     tournament's existence is not disclosed.
- **Standard envelope** on every path. The route currently returns a raw body
  (`res.json(analytics)`) and `{ error: '...' }` on failure — inconsistent with every sibling route,
  and unreadable by the frontend's error handling, which expects `error.code`.
- The `'Unknown'` sentinel is gone entirely.

### 4.2 Mounting

`routes/index.ts` gains an import and mounts it at `/tournaments`, **before** `tournamentRoutes`:

```ts
router.use('/tournaments', tournamentAnalyticsRoutes);
router.use('/tournaments', tournamentRoutes);
```

Verified no path collision: `tournaments.ts` defines no `/analytics/*`, no `/:id/analytics` and no
`/:id/feedback` (full route list checked). The router's other two routes become live as a
consequence — `/tournaments/analytics/trends` and `/tournaments/:id/feedback` — which is flagged in
§6 rather than silently ignored, since making a state-changing route live is not free.

### 4.3 Frontend

- `tournamentApi.getTournamentAnalytics(id)` reuses **`bracketRequest`**, which attaches
  `x-device-id`. This is the point: a logged-out, device-based organizer must be able to read their
  own private tournament, which is exactly why `bracketRequest` exists (Story 6.7 T05).
- `TournamentAnalyticsScreen`:
  - calls the new method instead of `getTournamentStats`;
  - `AnalyticsData` becomes the response type — no `as any`, no envelope read, no `/stats`.
- Reachability: register a `TournamentAnalytics` screen in `TournamentsStackNavigator`
  (`{ tournamentId, tournamentName }` params, matching what the screen already reads via
  `useRoute()`), plus an entry point from `TournamentDetailScreen`.

### 4.4 What is deliberately not changed

- `TournamentAnalyticsService` computation — it is correct and already has its own suite
  (`services/__tests__/tournamentAnalyticsService.test.ts`). This story is wiring, not maths.
- The *other*, mounted endpoint `GET /analytics/tournament/:tournamentId` (`routes/analytics.ts:173`)
  which reads the 4-column `tournament_analytics` table. Different data source, different
  granularity; left alone and its divergence recorded.
- `TournamentStats` type drift — separate defect.

## 6. Known consequences / follow-ups

- **`/tournaments/analytics/trends` and `POST /tournaments/:id/feedback` go live** as a side effect
  of mounting the router. Both were written and guarded but never reachable. Feedback is
  state-changing and has no route-level tests; smoke coverage is added, and fuller coverage is
  flagged.
- `routes/tournament-analytics.ts` declares a local `AuthRequest` whose `user.name` field is never
  populated (see §3). After this change the route no longer reads `name`; the misleading local
  interface is removed if nothing else in the file needs it.

## 8. Follow-up: `GET /tournaments/analytics/trends` (same commit series)

§6 flagged that mounting the router made two routes live for the first time. `POST /:id/feedback`
was repaired by the Story 6.8 session (`feedback.identity.test.ts`). `/analytics/trends` was left
with no route-level tests and still speaking the old contract. This closes that.

### 8.1 FIX-5 — the response contract

The route emitted a bare `{ trends, filters, timestamp }` on success and `{ error: '...' }` on
failure. It now uses the standard envelope like its sibling in the same file, so the frontend's
error handling (`error.code`) can read it. **Not a breaking change:** `grep -rn 'analytics/trends'`
across the frontend returns zero hits — there was no consumer.

### 8.2 FIX-6 — `limit` was coerced, not parsed

```ts
take: Number(limit)   // Number('abc') === NaN  → Prisma rejects → 500
```

A malformed query string produced a 500. `limit` is now parsed and clamped to `1..100`, falling
back to `10` for `NaN`, `0`, or negatives. `filters.limit` reports the **effective** value, not
the requested one.

### 8.3 NOT fixed — `requireRole(['ORGANIZER', 'ADMIN'])` is ADMIN-only

**Found while writing the authorization tests, and left alone deliberately.** Changing an
authorization guard is a product decision, not a defect fix.

`requireRole` in `middleware/auth.ts:150` compares `allowedRoles.includes(req.user.role)`.
`req.user.role` is a `UserRole`, and `UserRole` is exactly `OWNER | PLAYER | ADMIN`
(`schema.prisma:831-835`). **There is no `ORGANIZER` member.** So the string can never match and
the guard degrades to **ADMIN-only** — while the handler's own `organizerUserId: user.id` clause
exists precisely to let an organizer see their own tournaments. That clause is unreachable for
every non-admin.

`'ORGANIZER'` is a real identifier, but of a **different role system**: `PlayerRole`
(`middleware/permissions.ts:30`), which is session-scoped and resolved from `MvpPlayer.role`.
`permissions.ts` exports its own `requireRole(requiredRole: PlayerRole, action)` — the
account-level one from `auth.ts` is the wrong helper for this string.

Same class as the `req.user.name` bug in §3: **an identifier that does not exist in the domain,
silently making a guard inert.** Confirmed present in six places:

| File | Guard | Effective meaning |
|---|---|---|
| `routes/tournament-analytics.ts:138` | `requireRole(['ORGANIZER','ADMIN'])` | **ADMIN only** |
| `routes/pairings.ts:25,209,314,385,600` | `requireRole(['OWNER','ORGANIZER'])` | **OWNER only** |

The `pairings.ts` cases are lower impact — `OWNER` is plausibly the intended role there anyway.
The trends case is the one that contradicts its handler.

**Recommended, not done:** decide whether `/analytics/trends` should be
(a) organizer-scoped — drop `requireRole` for `optionalAuth` and rely on the visibility clause
that is already there, or (b) genuinely admin-only — then delete the dead `organizerUserId`
clause so the code stops claiming otherwise. Either way the `'ORGANIZER'` string should be
removed from every `auth.ts` `requireRole` call site, because it cannot ever match.
