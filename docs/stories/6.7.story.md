# Story 6.7: Tournament Bracket Management

## Status: Draft

## Story

As a tournament organizer,
I want brackets generated and managed through their lifecycle,
So that tournaments run correctly and progression is tracked.

## Context Source

- Source Document: docs/epics/epic-6.md (Story 6.7, Workstream WS7)
- Enhancement Type: Brownfield feature completion on existing bracket services
- Existing System Impact: Extends `tournamentBracketService`/`bracketService` and tournament models to a full lifecycle

## Acceptance Criteria

**Functional Requirements:**

1. `backend/src/services/tournamentBracketService.ts` and `backend/src/services/bracketService.ts` generate valid single- and double-elimination brackets
2. Byes, seeding, and non-power-of-two player counts handled correctly
3. Bracket lifecycle (create → progress → complete) persists to `TournamentRound`, `TournamentMatch`, and `TournamentGame`
4. Standings and ranking changes integrate with `backend/src/services/tournamentAnalyticsService.ts`

**Integration Requirements:**

5. Existing `routes/tournaments.ts` contracts preserved; new endpoints are additive
6. Organizer UI integrates with existing tournament screens and patterns
7. Bracket state feeds real-time updates (Story 6.4) and analytics (Epic 5)
8. Player rankings update via existing `services/rankingService.ts`

**Quality Requirements:**

9. Bracket generation correctness = 100% across seeded/bye/odd-count cases
10. Tournament completion rate > 80%
11. Progression and result recording covered by unit and integration tests
12. Rollback/correction path for mistaken match results

**Non-Functional Requirements:**

13. Generation is deterministic given the same seed/inputs
14. Schema changes are additive and backward compatible
15. Permissions enforce organizer-only bracket mutation (`middleware/permissions.ts`)
16. Large tournaments (e.g., 64 players) generate without UI blocking

## Dev Technical Guidance

### Existing System Context

`backend/src/services/tournamentBracketService.ts` defines `BracketMatch`, `TournamentBracket`, and generation structures; `backend/src/services/bracketService.ts` also exists. Tournament Prisma models are extensive: `Tournament`, `TournamentPlayer`, `TournamentRound`, `TournamentMatch`, `TournamentGame`, `TournamentGameSet`, `TournamentResult`, `TournamentAnalytics`, `TournamentFeedback`. `routes/tournaments.ts` and `services/tournamentService.ts` provide the API/service layer. The gap is a complete, tested lifecycle and organizer UI.

### Integration Approach

Build on the existing bracket structures: implement/verify generation (seeding, byes, double-elimination), persist rounds/matches, and drive progression by recording results and advancing winners. Wire standings into `tournamentAnalyticsService` and ranking updates, and emit real-time events after persistence.

### Technical Constraints

- Organizer-only mutation via `requireOrganizer`.
- Deterministic generation for the same inputs (documented seeding rules).
- Do not break existing tournament response shapes.

## Testing

### Validation Steps

1. Generate brackets for 4, 5, 8, and 16 players; verify seeds and byes
2. Play a full tournament to completion; verify progression and standings
3. Correct a mistaken result and verify bracket recomputation
4. Verify only organizers can mutate brackets
5. Run `npm run typecheck` and `npm test` in `backend`; lint/test in `frontend/Rally`

### Test Scenarios

- Seeded/unseeded generation
- Bye handling and odd counts
- Double-elimination losers' bracket
- Result correction/rollback
- Permission enforcement

## Risk Assessment

- **Primary Risk:** Incorrect bracket progression corrupts tournament results.
- **Mitigation:** Deterministic generation, comprehensive case matrix, and result-correction path.
- **Rollback:** Revert to prior bracket state via correction; disable new endpoints without affecting existing tournaments.

**Compatibility Verification:**

- [ ] No breaking changes to existing APIs
- [ ] Database changes are additive only
- [ ] UI changes follow existing design patterns
- [ ] Performance impact is negligible
