# Story 6.10: API Response Envelope Contract Fix

## Status: Delivered (verified)

## Story

As a player using the Rally app,
I want tournament, session, ranking and social screens to display real data,
So that the app is usable rather than silently empty or crashing.

## Context Source

- Origin: defect found during Story 6.7 recon (`docs/stories/6.7.design.md`, section 3a).
- Enhancement Type: **Defect remediation** (cross-cutting frontend contract fix).
- Existing System Impact: changes one shared method (`ApiService.request`) and one
  consumer that was compensating for the defect. No backend change.

## Problem statement

`ApiService.request<T>()` declares `Promise<ApiResponse<T>>` where
`ApiResponse<T>.data?: T` — i.e. **`data` is the payload**. At runtime it assigns
`data = await response.json()`, which is the backend's **whole envelope**
(`{ success, data: <payload>, message, timestamp }`). So `data` is one level too
high, and every consumer that trusts the declared contract reads the envelope.

Verified backend envelope (read from source, not inferred):

| Endpoint | Body |
|---|---|
| `GET /tournaments` | `{ success: true, data: { tournaments, total, limit, offset } }` |
| `GET /tournaments/:id` | `{ success: true, data: tournament }` |
| `GET /mvp-sessions/join/:shareCode` | `{ success: true, data: { session } }` |

## Acceptance Criteria

**Functional**

1. `ApiService.request<T>()` resolves `data` to the **payload**, honouring the declared
   `ApiResponse<T>.data?: T` contract.
2. Envelope detection is **precise**: unwrap only when the parsed body is a non-null
   object with `typeof body.success === 'boolean'`. Any other body (raw array, plain
   object, primitive) passes through unchanged.
3. `message` and `timestamp` continue to be populated from the envelope when present.
4. The error path is unchanged: `{ success: false, error: { code, message, details } }`,
   and a direct-online `409 VERSION_CONFLICT` still lands in `sync.conflicts[]` (AC 7
   of Story 6.4).
5. The offline/queued optimistic path is unchanged (`{ success: true, data: {} }`).

**Integration**

6. Every existing consumer receives the shape it was written against:
   - `tournamentApi` (6 sites) — payload
   - `rankingApi` (6 sites) — payload
   - `mvpApiService` (via `SessionContext` / `SessionOverviewScreen` / `realTimeService`) — payload
   - `socialApi` (4 consuming screens) — payload
   - `authSlice` login/register — still resolves `{ user, tokens }`
7. `TournamentAnalyticsScreen.tsx` is corrected: it currently reads the **envelope**
   (`(response as any).data`) and so passes the wrong object to `setAnalytics`. After the
   fix it must pass the payload. This is **behaviour-preserving**, not a repair — the
   screen's `AnalyticsData` shape does not match the backend's stats payload (a separate,
   pre-existing defect, out of scope). See design §3.

**Quality**

8. Frontend `npx tsc --noEmit` is clean.
9. Frontend jest failure count is **not worse** than the recorded baseline, proven by
   reverting only the changed files and re-running.
10. Regression tests cover `request()` unwrapping: enveloped body → payload; raw body →
    unchanged; error body → unchanged.
11. A **runtime probe** proves the seam end-to-end (real `apiService` against a recording
    HTTP server returning a real backend-shaped envelope), not merely types.

**Non-functional**

12. No change to `ApiService`'s public method signatures (`get`/`post`/`put`/`delete`/
    `request`), so no consumer needs an import change.
13. The fix is made **once**, centrally — not duplicated across call sites.

## Out of scope

- Removing the now-redundant defensive `extractAuthPayload` dual-shape handling in
  `authSlice.ts` (it stays harmless and keeps the change reversible).
- Any backend change.
- `backend/dist` tracking hygiene (tracked separately).
