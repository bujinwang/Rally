# Story 6.4: Hardened Real-Time Sync

## Status: Draft

## Story

As a player,
I want rotations, scores, and analytics to update live and correctly,
So that everyone in a session sees the same state without manual refresh.

## Context Source

- Source Document: docs/epics/epic-6.md (Story 6.4, Workstream WS4)
- Enhancement Type: Brownfield real-time hardening
- Existing System Impact: Extends Socket.io from single-instance wiring to scalable, event-driven updates

## Acceptance Criteria

**Functional Requirements:**

1. `backend/src/config/socket.ts` scales beyond a single instance via a Socket.io adapter/pub-sub with documented deployment topology
2. Auth-aware socket connections tied to identity from Story 6.1 (with guest connections still supported)
3. Tournament analytics real-time placeholder (`backend/src/routes/tournament-analytics.ts:157`) replaced with event-driven updates
4. Rotation, scoring, and player-status events emitted from authoritative server state

**Integration Requirements:**

5. Existing socket events used by `frontend/Rally/src/services/socketService.ts`, `hooks/useMessaging.ts`, and `hooks/useNotificationManager.ts` remain compatible
6. `frontend/Rally/src/services/discoveryApi.ts` real-time discovery continues to work
7. Cache (Story 6.2) and socket state remain consistent on invalidation
8. No duplicate or lost events on reconnect

**Quality Requirements:**

9. Event delivery p95 < 300 ms; reconnect success > 99%
10. Idempotent, ordered event handling verified with tests
11. Missed-event recovery on reconnect (resume or refetch) verified
12. Load tested with concurrent sessions/connections

**Non-Functional Requirements:**

13. Socket auth uses the same token/identity model as REST
14. Namespace/room isolation prevents cross-session data leaks
15. Adapter config (e.g., Redis pub/sub) via env, not hardcoded
16. Graceful degradation to polling when sockets are unavailable

## Dev Technical Guidance

### Existing System Context

`backend/src/config/socket.ts` initializes Socket.io, uses `prisma` and `cacheService`, and serves real-time discovery. `backend/src/socket/notificationHandlers.ts` handles socket notifications. Frontend socket usage exists in `socketService.ts` and several hooks. The gap is horizontal scale (no adapter), auth tying, and the tournament-analytics real-time placeholder.

### Integration Approach

Add a Socket.io Redis adapter configured from env, authenticate connections with the JWT from Story 6.1 while permitting anonymous/guest sockets, define explicit room names per session/tournament, and emit domain events from the authoritative service layer after persisted changes. On the frontend, add reconnect/resume handling and fall back to polling.

### Technical Constraints

- Never emit unpersisted state as authoritative.
- Keep existing event names/payloads stable; add new events additively.
- Adapter infra must not be required in local dev (in-memory adapter fallback).

## Testing

### Validation Steps

1. Connect two clients to one session and verify live updates
2. Verify auth and guest connections both work; cross-session isolation holds
3. Kill/reconnect a client and confirm no lost/duplicated events
4. Scale to multiple server instances and verify cross-instance delivery
5. Run `npm run typecheck` and `npm test` in `backend`; `npm run lint` and `npm test` in `frontend/Rally`

### Test Scenarios

- Concurrent session event fan-out
- Reconnect and missed-event recovery
- Unauthorized socket handshake rejection
- Polling fallback when sockets fail

## Risk Assessment

- **Primary Risk:** Duplicate or lost events corrupt session state.
- **Mitigation:** Server-authoritative emits, event ids, idempotent handlers, and reconnect recovery tests.
- **Rollback:** Disable the adapter (single-instance mode) and revert to polling.

**Compatibility Verification:**

- [ ] No breaking changes to existing APIs
- [ ] Database changes are additive only
- [ ] UI changes follow existing design patterns
- [ ] Performance impact is negligible
