# Story 6.1: Authenticated Identity and Auth Hardening

## Status: Draft

## Story

As a Rally user,
I want to register or log in and have my session activity attributed to a real account,
So that ownership, permissions, and personalization are trustworthy across devices.

## Context Source

- Source Document: docs/epics/epic-6.md (Story 6.1, Workstream WS1)
- Enhancement Type: Brownfield integration and hardening of existing auth scaffolding
- Existing System Impact: Adds optional/required auth to the MVP session flow without breaking guest join

## Acceptance Criteria

**Functional Requirements:**

1. Registration, login, and refresh endpoints in `backend/src/routes/auth.ts` work end-to-end against the `User` model
2. Access + refresh tokens issued via `backend/src/utils/jwt.ts` with rotation, revocation, and expiry handling
3. `backend/src/routes/mvpSessions.ts` supports optional/required auth with ownership enforced on mutating routes
4. Existing guest share-link join remains fully functional without login (no regression)
5. Authenticated users can claim guest-created sessions/players by device ID
6. RBAC enforced via `middleware/auth.ts` (`authenticateToken`, `requireRole`) and `middleware/permissions.ts` (`requireSessionOwner`, `requireOrganizer`) with tests
7. Password strength (bcrypt via `utils/password.ts`) and `strictLimiter`-style rate limiting verified on auth endpoints
8. OAuth paths (`routes/oauth.ts`, `services/oauthService.ts`) verified and documented

**Integration Requirements:**

9. Existing session/player API contracts and response envelopes remain unchanged for unauthenticated callers
10. Frontend `frontend/Rally/src/services/sessionApi.ts` gains token handling without changing join behavior
11. Rate limiting continues to apply to auth endpoints
12. Prisma schema changes are additive and backward compatible

**Quality Requirements:**

13. Unit tests for token issuance/refresh/revocation and password utilities
14. Integration tests for register → login → access-protected-route → refresh
15. Regression tests proving the guest join path still works
16. Auth failures never leak sensitive data or stack traces

**Non-Functional Requirements:**

17. Refresh token rotation and server-side validity check (`isRefreshTokenValid`)
18. Secrets read from environment; no hardcoded keys
19. Auth endpoints respond within 500 ms under normal load
20. Privacy review for stored identity data

## Dev Technical Guidance

### Existing System Context

The `User`, `UserSettings`, and related models exist in `backend/prisma/schema.prisma`. `routes/auth.ts` already implements register/login against the `User` model with `JWTUtils` and `PasswordUtils`, and is mounted at `/auth` in `routes/index.ts`. `routes/oauth.ts` is mounted at `/oauth`. `utils/jwt.ts` provides access/refresh tokens plus `storeRefreshToken` and `isRefreshTokenValid`. The key gap is that `routes/mvpSessions.ts` applies **no** auth middleware today, so identity is not enforced in the core flow.

### Integration Approach

Add `optionalAuth` and `requiredAuth` middleware (built on `authenticateToken`) and apply them selectively to `mvpSessions.ts`: reads and guest join stay open, mutating/ownership operations require or use identity. Add a claim endpoint that links device-created sessions/players to the authenticated user. Wire the frontend to send the access token when present and transparently refresh on 401.

### Technical Constraints

- Guest join must work with no account and no token.
- Do not break existing response envelopes or error codes.
- Token secrets and expiries via env (`JWT_SECRET`, `JWT_REFRESH_SECRET`, expiries).
- Rate limit auth endpoints; do not weaken existing `rateLimiter` tiers.

## Testing

### Validation Steps

1. Register a user and log in; verify tokens and DB state
2. Call a protected route with/without a valid token
3. Refresh an expired access token; verify rotation and revocation
4. Join a session via share link with no account (must succeed)
5. Claim a guest session as an authenticated user; verify ownership transfer
6. Run `npm run typecheck` and `npm test` in `backend`

### Test Scenarios

- Successful and failed registration/login
- Token refresh, reuse, and revocation
- Unauthorized access attempts
- Guest join regression
- Device-ID claim conflict handling

## Risk Assessment

- **Primary Risk:** Adding auth breaks the frictionless guest join flow that defines the MVP.
- **Mitigation:** Dual-path middleware, token-free guest path, and explicit regression tests; feature-flag rollout.
- **Rollback:** Disable auth middleware application on `mvpSessions.ts`; routes remain additive.

**Compatibility Verification:**

- [ ] No breaking changes to existing APIs
- [ ] Database changes are additive only
- [ ] UI changes follow existing design patterns
- [ ] Performance impact is negligible
