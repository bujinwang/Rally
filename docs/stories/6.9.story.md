# Story 6.9: Mobile Release and Push Notifications

## Status: Draft — recon complete, design proposed (`6.9.design.md`), awaiting two decisions

## Story

As a player,
I want the app from the store with useful notifications,
So that I never miss a session or match.

## Context Source

- Source Document: docs/epics/epic-6.md (Story 6.9, Workstream WS9)
- Enhancement Type: Brownfield release and push-notification completion
- Existing System Impact: Ships the existing Expo app to stores and wires the existing push scaffolding end-to-end

## Acceptance Criteria

**Functional Requirements:**

1. Production iOS and Android builds via Expo EAS with a documented, repeatable release pipeline
2. Push delivery wired end-to-end using `expo-server-sdk`, the `PushToken` model, and `backend/src/routes/notifications.ts`
3. Notification preferences (`NotificationPreferences`) respected; opt-out honored
4. App Store and Play Store approval achieved

**Integration Requirements:**

5. Push targeting uses identity from Story 6.1 (and guest tokens where allowed)
6. Notification flows integrate with `services/notificationService.ts` via its public entry points `registerPushToken` and `unregisterPushToken`. (`sendPushNotification` is `private` — invoked internally by the notification-trigger paths, not a public integration point. NOTE: the mounted `POST /notifications/register` route currently reimplements token storage itself rather than calling this service — see 6.9.design.md F3.)
7. Frontend `expo-notifications` (`hooks/useNotificationManager.ts`, `services/NotificationService.ts`) aligns with backend tokens
8. Release builds point at production API and observability (Story 6.3)

**Quality Requirements:**

9. Crash-free sessions > 99.5%
10. Push opt-in > 60%
11. Delivery, preference, and opt-out covered by tests
12. Staged rollout and documented rollback procedures

**Non-Functional Requirements:**

13. Store policy compliance (privacy manifest, data-safety declarations)
14. Secrets/credentials stored securely in CI, not in the repo
15. Build reproducibility documented
16. Notification payloads contain no sensitive data

## Dev Technical Guidance

### Existing System Context

The frontend is Expo-based (`frontend/Rally`) with `expo-notifications`, `expo-application`, and `expo-image-picker` installed. Backend has `expo-server-sdk`, a `PushToken` model, `Notification`/`NotificationPreferences` models, `routes/notifications.ts`, `routes/notifications` handlers under `backend/src/socket/notificationHandlers.ts`, `services/notificationService.ts` (with `registerPushToken`/`unregisterPushToken`/`sendPushNotification`), and `utils/notificationHelper.ts`. There is no store release or production push pipeline today.

### Integration Approach

Configure Expo EAS build/submit profiles, register device tokens on login (Story 6.1) and on app start, honor `NotificationPreferences`, and send notifications server-side through `expo-server-sdk` after domain events (match reminders, session changes). Gate release on crash-free and monitoring signals, and stage the rollout.

### Technical Constraints

- No credentials in the repo; use CI secrets.
- Guest users may receive only consented, non-sensitive notifications.
- Store review requires stable builds; freeze scope during review.

## Testing

### Validation Steps

1. Build release binaries for iOS and Android
2. Register a token, trigger a notification, verify delivery
3. Toggle preferences/opt-out and verify suppression
4. Verify no sensitive data in payloads
5. Check crash-free rate and opt-in metrics post-rollout
6. Run `npm run lint` and `npm test` in `frontend/Rally`

### Test Scenarios

- Token registration/unregistration
- Delivery and suppression by preference
- Invalid/stale token cleanup
- Release build smoke test
- Staged rollout and rollback

## Risk Assessment

- **Primary Risk:** A store release ships with undetected regressions and is hard to recall.
- **Mitigation:** Crash-free gate, monitoring from Story 6.3, staged rollout, and documented rollback.
- **Rollback:** Halt staged rollout; publish a fixed build.

**Compatibility Verification:**

- [ ] No breaking changes to existing APIs
- [ ] Database changes are additive only
- [ ] UI changes follow existing design patterns
- [ ] Performance impact is negligible
