## Dev Technical Guidance

### Existing System Context

The frontend is Expo-based (`frontend/Rally`) with `expo-notifications`, `expo-application`, and
`expo-image-picker` installed. Backend has `expo-server-sdk` (installed, now used by
`services/pushTransport.ts`), a `PushToken` model, `Notification`/`NotificationPreferences` models,
`routes/notifications.ts`, `backend/src/socket/notificationHandlers.ts`, and
`utils/notificationHelper.ts` (the live send path).

**Retired:** `services/notificationService.ts` was deleted in `b12d3e1`. Recon (`6.9.design.md` F3)
found it was **broken against the live schema** (its raw SQL referenced `player_id`/`is_active`/… which
do not exist — the real columns are camelCase), imported only by its own mock-based test, and had never
executed. Its three correct, DB-free helpers were ported to `services/notificationPreferences.ts`.

### Integration Approach

Register device tokens on login (Story 6.1) and on app start, honour `NotificationPreferences`
(opt-out + quiet hours), and send notifications server-side through `expo-server-sdk` after domain
events (match reminders, session changes). Enforce a **deny-by-default guest allow-list** so
device-only tokens receive only non-sensitive, session-mechanics notifications (Q2, approved).

### Technical Constraints

- No credentials in the repo; use CI secrets. (Phase-1 work needs none.)
- Guest users may receive only consented, non-sensitive notifications (Q2 allow-list).
- Store review requires stable builds; freeze scope during review. (Phase 2.)

## Testing

### Validation Steps (Phase 1)

1. Register a token (device-only and account) → verify the row is stored keyed on `deviceId`/`userId`.
2. Trigger a domain event (session reminder, player joined, score recorded) → verify the transport is
   invoked with the correct payloads and that delivery targets the registered tokens.
3. Toggle preferences/opt-out and quiet hours → verify suppression.
4. Verify a device-only token receives only guest-allow-listed types.
5. Verify no token material and no sensitive data appears in payloads or logs.
6. Run the backend test suite (`jest --forceExit --runInBand`) and `npm run lint` / `npm test` in `frontend/Rally`.

### Test Scenarios (Phase 1)

- Token registration/unregistration (device-only and account)
- Delivery targets the correct identity keying (F9)
- Transport: batching, index-safe ticket correlation, per-token error isolation, `DeviceNotRegistered` pruning
- Preference suppression by type + opt-out + quiet hours
- Guest allow-list (deny-by-default)
- No sensitive data in payloads (AC 16)

### Moved to Phase 2 testing

- Release build smoke test
- Staged rollout and rollback (mechanics)
- Crash-free / opt-in measurement
