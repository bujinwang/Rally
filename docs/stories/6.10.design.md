# Story 6.10 — Design: API Response Envelope Contract Fix

**Status: design accepted, implementation pending.**

---

## 1. The defect, stated precisely

`frontend/Rally/src/services/apiService.ts`, `ApiService.request<T>()`:

```ts
interface ApiResponse<T> { success: boolean; data?: T; message?: string; error?: {...}; timestamp: string; }
// ...
const data = await response.json();          // <-- the WHOLE backend envelope
return { success: true, data, message: data.message, timestamp: data.timestamp || ... };
```

The declared type says `data?: T`. The runtime value is
`{ success, data: <T>, message, timestamp }`. **One level too high.**

Backend envelope, read from source (`backend/src/routes/tournaments.ts`,
`backend/src/routes/mvpSessions.ts`) — not inferred:

| Endpoint | Line | Body |
|---|---|---|
| `GET /tournaments` | `tournaments.ts:157` | `{ success: true, data: result }` where `result = { tournaments, total, limit, offset }` |
| `GET /tournaments/:id` | `tournaments.ts:192` | `{ success: true, data: tournament }` |
| `GET /tournaments/:id/stats` | `tournaments.ts` | `{ success: true, data: ... }` |
| `GET /mvp-sessions/join/:shareCode` | `mvpSessions.ts:665` | `{ success: true, data: { session: {...} } }` |

A grep for `res.json({ success: true, session` / `player` / `tournament` (i.e. a payload
at top level with **no** `data` key) returns **zero hits** — the `data` key is the
consistent convention.

---

## 2. The decisive question: fix centrally, or per call site?

Story 6.7's wrap-up recorded a recommendation to fix **per call site**, reasoning that
"unwrapping centrally would change behaviour for every consumer repo-wide." That
reasoning was never tested against the consumer set. It has now been.

**Every consumer was read, and the expectation at each site was recorded.** `grep` for
`.data.data` across `frontend/Rally/src` returns **zero hits** — no caller anywhere
compensates for the extra level.

| # | Consumer site | Code reads | Expects `res.data` to be | Today | After central fix |
|---|---|---|---|---|---|
| 1 | `SessionOverviewScreen.tsx:218` (mvp) | `response.data?.session` | payload `{session}` | **broken** | ✅ fixed |
| 2 | `CommunityFeedScreen.tsx:40` (social) | `setFeed(response.data)` | payload `CommunityFeed` | **broken** | ✅ fixed |
| 3 | `PrivacySettingsScreen.tsx:35` (social) | `setSettings(response.data)` | payload `PrivacySettings` | **broken** | ✅ fixed |
| 4 | `ShareButton.tsx:49` (social) | `const { shareUrl, preview } = response.data` | payload `{share, shareUrl, preview}` | **broken** | ✅ fixed |
| 5 | `TournamentListScreen.tsx:45` (tourn) | `response.tournaments` | payload `TournamentListResponse` | **broken** | ✅ fixed |
| 6 | `TournamentDetailScreen.tsx:103` (tourn) | `setTournament(await getTournamentById())` | payload `Tournament` | **broken (throws)** | ✅ fixed |
| 7 | `TournamentCreateScreen.tsx:98` (tourn) | uses returned `id` | payload `Tournament` | **broken (`undefined` id)** | ✅ fixed |
| 8 | `RankingScreen.tsx:42,44` (ranking) | `data.map(...)` | payload array | **broken** | ✅ fixed |
| 9 | `authSlice.ts:41,58` (apiService) | `extractAuthPayload(response.data)` | *either* shape | works (defensive) | ✅ still works |
| 10 | **`TournamentAnalyticsScreen.tsx:58`** | `(response as any).data` | **the envelope** | works *by accident* | ⚠️ **needs a 1-line edit** |

**Result: 9 of 10 sites expect the payload; exactly 1 expects the envelope, and that one
is itself reading the wrong layer.** The declared type contract (`data?: T`) agrees with
the 9. The defect is in `apiService`, and the fix belongs there — once, not eleven times.

Site 10 is the "accidentally works" case flagged in the 6.7 recon. It unwraps `.data`
*itself* and so survived. It is corrected in this story (AC 7).

`authSlice.ts` already carries a defensive shim with a comment naming the bug:

```ts
// `{ success, data: { user, tokens } }` and apiService wraps the whole body
// again as `{ success, data: <body> }`. Accept either shape.
const extractAuthPayload = (payload: any) => ({
  user: payload?.data?.user ?? payload?.user ?? null,
  tokens: payload?.data?.tokens ?? payload?.tokens ?? null,
});
```

A previous engineer hit this defect, worked around it locally, and did not fix the cause.
That shim keeps working after the fix (`payload?.data?.user` → `undefined`, falls through
to `payload?.user`), which is why it is left in place — it makes the change reversible.

## 3. The fix

Single edit in `ApiService.request`, replacing the success-path return:

```ts
const body = await response.json();

// The backend wraps every payload in `{ success, data, message, timestamp }`.
// `ApiResponse<T>.data` is declared as the *payload*, so unwrap one level —
// but only when the body really is an envelope. A raw array or a plain object
// (no boolean `success`) passes through untouched.
const isEnvelope =
  body !== null && typeof body === 'object' && typeof body.success === 'boolean';
const payload = isEnvelope ? body.data : body;

return {
  success: true,
  data: payload,
  message: isEnvelope ? body.message : body?.message,
  timestamp: (isEnvelope ? body.timestamp : body?.timestamp) || new Date().toISOString(),
};
```

Design notes:

- **Detection by `typeof body.success === 'boolean'`, not by `'data' in body`.** A
  payload may legitimately contain a `data` key of its own; keying off `success` avoids
  unwrapping a payload that happens to look like an envelope.
- **`message`/`timestamp` are read before unwrapping**, because they live on the
  envelope, not the payload.
- **No signature change** (AC 12) — `get`/`post`/`put`/`delete`/`request` are untouched,
  so no consumer import or call site changes.
- **Untouched paths:** the `!response.ok` branch (error envelope, `409 VERSION_CONFLICT`
  surfacing) and both offline/queued optimistic returns. AC 4 and AC 5 pin these.

### Compensating edit (AC 7)

`components/TournamentAnalyticsScreen.tsx:58`:

```diff
-      setAnalytics((response as any).data);
+      setAnalytics(response as any);
```

**Correction to the Story 6.7 write-up, found during implementation.** The 6.7 memory
recorded this site as "accidentally works". That is only half true, and the difference
matters:

- `GET /tournaments/:id/stats` returns `data = { totalPlayers, maxPlayers, totalMatches,
  completedMatches, completionRate, status }` (`services/tournamentService.ts:381`).
- This screen's `AnalyticsData` wants `{ totalRegistered, participationRate,
  completionRate, matchesCompleted, totalMatches, bracketEfficiency, averageUpsets,
  rankingChanges }`.

The two shapes **overlap on only two fields**. So today the screen is not "working" —
it renders `completionRate` and `totalMatches` and `undefined` for the other six.

`setAnalytics(response as any)` therefore **preserves existing behaviour exactly** (the
same object is passed, before and after), which is the correct scope for this story. It
does **not** make the screen correct — that requires reconciling `AnalyticsData` with the
backend payload, which is a separate, pre-existing defect and is explicitly out of scope
here. The same drift exists in `tournamentApi`'s `TournamentStats` type, which declares
`totalGames`/`totalSets`/`currentRound`/`tournamentProgress` that the backend never sends.

Flagging this rather than quietly "fixing" it: silently reshaping the payload here would
have looked like an improvement while inventing data the backend does not provide.

## 4. Blast radius and why it is safe

- **Backend:** no change.
- **`ApiService` subclasses:** `MvpApiService extends ApiService` — inherits the fix and
  its callers (rows 1) expect the payload, so it improves.
- **`realTimeService.ts:136,266`** calls `mvpApiService.getSessionByShareCode` — payload
  expected, improves.
- **`SessionContext.tsx:82,115,136`** — same.
- **Tests:** `__tests__/social-components.test.tsx` and `__tests__/sessionApi.test.ts`
  touch this surface and are checked in AC 9 (baseline-compared, not assumed).
- **Reversibility:** the change is one method plus one line; the `authSlice` shim means
  even a partial revert degrades rather than breaks.

## 5. Verification plan

1. `npx tsc --noEmit` in `frontend/Rally` → clean (AC 8).
2. Frontend jest before/after; prove any failures pre-existing by reverting **only** the
   two changed files (`cp` aside, never `git checkout`) and re-running (AC 9).

   unchanged; raw object without `success` → unchanged; error body → `success:false`
   with `error.code` preserved (AC 10).
4. **Runtime probe (AC 11)** — the part that actually proves it. Unit tests that mock
   `authFetch` prove nothing about the real seam (the same lesson Story 6.7's T05 QA
   taught). The probe: spin a recording HTTP server that returns a byte-exact
   `{success:true,data:{tournaments:[...],total:1,...}}` body, point a real
   `ApiService` instance at it, and assert `get('/tournaments').data.tournaments` is the
   array — then repeat for the pre-fix build and show it is `undefined`. Broken state and
   fixed state, same probe.
5. Independent adversarial QA pass (per SOP): *"try to falsify these claims"*.

### FIX-1 — a jest load trap hit during implementation

`apiService` → `syncManager` → `deviceService` → `expo-constants`, whose published build is
untranspiled ESM, killed both new suites at load with
`SyntaxError: Cannot use import statement outside a module` (0 tests run). Resolved by
mocking the `../deviceService` boundary — the documented remedy in this repo. A 0-test
load failure is worse than a failing test, so this was fixed rather than worked around.

### FIX-2 — my own first consumer probe was wrong

The initial `apiService.consumers.test.ts` run failed
`getTournamentById` with `Cannot read properties of undefined (reading 'scoringSystem')`.
Cause was the **test's** stub server, which only routed the exact path `/tournaments` and
404'd `/tournaments/t1` — not a product defect. Added the `/:id` route; all 4 then passed.
Recorded because a red probe is easy to misread as a red product.

### Deviations from the design as written

- **AC 7's framing was corrected mid-implementation.** The design (following the 6.7
  write-up) called this screen "accidentally working". Reading the backend payload showed
  it is only partially populated — see §3. The edit is behaviour-preserving, and the
  underlying shape mismatch is reported as out of scope rather than silently reshaped.
- **§2's consumer table was incomplete on first pass.** A wider sweep found six further
  `response.data` readers (`SessionHistoryScreen`, `MatchHistoryScreen`, `MySessionsScreen`,
  `analytics/AnalyticsScreen`, `PredictionDashboardScreen`, `AnalyticsDashboardScreen`).
  All six call services that never import `apiService` (`sessionHistoryApi`,
  `matchHistoryApi`, `sessionApi`, `analyticsApi`, `predictionApi`), so they are
  **unaffected** — verified by grepping every `from '.*apiService'` importer, which returns
  exactly five files. No action needed, but the design's claim of completeness was wrong
  and is corrected here.
