# Story 6.9 — Design: Mobile Release and Push Notifications

**Status: recon complete, design proposed. No implementation started.**

This document is the recon deliverable. The headline is that Story 6.9 is **not** "finish the
wiring" — the push pipeline is **broken at the database level**, and roughly half the story's
acceptance criteria are not verifiable from a development machine at all. Both need to be settled
before any code is written.

---

## 1. Headline findings

### F1 — BLOCKER: push token registration is impossible

`POST /notifications/register` writes:

```ts
// routes/notifications.ts:73-79
tokenRecord = await prisma.pushToken.create({
  data: { token: pushToken, playerId: deviceId, deviceId, platform, isActive: true },
});
```

But `PushToken.playerId` is a **required foreign key to `MvpPlayer.id`**:

```prisma
// prisma/schema.prisma:1695-1713
model PushToken {
  playerId String            // Reference to MvpPlayer
  player   MvpPlayer @relation(fields: [playerId], references: [id], onDelete: Cascade)
```

A device id is not an `MvpPlayer` id, so every call violates the constraint. **Verified against the
real database**, not inferred:

```
RESULT: THREW
  code : P2003
  meta : {"modelName":"PushToken","constraint":"push_tokens_playerId_fkey"}
  msg  : Foreign key constraint violated on the constraint: `push_tokens_playerId_fkey`
```

The route's `catch` turns that into `500 INTERNAL_ERROR "Failed to register push token"`
(`routes/notifications.ts:95-101`). So a real client can never register a token, and push
notification cannot work end-to-end regardless of what else is fixed.

This is the **same defect class as Story 6.8's D5** — `TournamentFeedback.playerId` held a
`User.id` while FK'ing to `MvpPlayer.id`. That one was found and repaired. This one is live.

### F2 — there is no push transport; it is a stub

```ts
// services/notificationService.ts:76-92
private static async sendToDevice(token: any, notificationData: NotificationData): Promise<void> {
  // In a real implementation, this would integrate with FCM/APNs
  // For now, we'll just log the notification
  console.log(`Sending push notification to ${token.platform} device:`, {
    token: token.token, title: notificationData.title, body: notificationData.body, data: notificationData.data,
  });
  // Simulate successful delivery
  return Promise.resolve();
}
```

It logs and resolves. AC 2 says delivery is wired "using `expo-server-sdk`" —
**`expo-server-sdk@^3.15.0` is installed in `backend/package.json` and imported nowhere in
`backend/src`.** It is a dead dependency.

### F3 — the service the story names is orphaned

`backend/src/services/notificationService.ts` is **599 lines with ~22 methods** — including
`registerPushToken`, `unregisterPushToken` and preferences CRUD, exactly what AC 2/3/6 name. It is
imported by **one file: its own test.**

Meanwhile the *mounted* route (`routes/notifications.ts`, 5 endpoints) reimplements token storage
itself. And the two halves use **different data-access paths to the same table**:

| | Access path |
|---|---|
| `routes/notifications.ts` (reachable) | `prisma.pushToken` (Prisma client) |
| `services/notificationService.ts` (orphaned) | `prisma.$queryRaw` on `push_tokens` (raw SQL) |

Two implementations of one concept, one of them unreachable. This is the **third** instance of the
orphaned-module pattern in Epic 6 (after 6.10's envelope consumer and 6.11's route + screen).

Good news: the raw SQL uses `$queryRaw` **tagged templates**, which Prisma parameterises — so
there is **no SQL injection** here. I checked specifically because `${}` interpolation in SQL
strings normally is one.

### F4 — AC 3 is unimplemented, not merely untested

`notificationPreferences` is read by **no production code**. The only references are inside the
orphaned service and its test. There is no opt-out path to honour.

### F5 — the frontend half is genuinely wired

Unlike the backend, this side is reachable and used:

| File | Imported by |
|---|---|
| `services/NotificationService.ts` | 5 files, incl. `App.tsx`, `AppNavigator.tsx` |
| `hooks/useNotificationManager.ts` | `SessionDetailScreen.tsx` |

`expo-notifications ~0.29.14` and `expo-application ~6.0.2` are installed. `expo-device` is
**absent** (may be needed to obtain a real device token).

So the frontend can *produce* a token. The backend cannot *accept* one. That asymmetry is the
shape of this story.

### F6 — AC 6 names a private method as public API

AC 6 lists `sendPushNotification` among the integration points. It is `private static`
(`notificationService.ts:52`). The story's spec and the code disagree.

### F7 — why the existing test never caught F1

`routes/__tests__/notifications.test.ts` **mocks Prisma** (line 5), so the FK is never enforced.
Its assertion then uses `objectContaining` and **omits `playerId` entirely**:

```ts
expect(prisma.pushToken.create).toHaveBeenCalledWith({
  data: expect.objectContaining({ token: 'tok-1', deviceId: 'dev-1', platform: 'ios', isActive: true }),
});
```

The test is green, and it is green *because* it does not look at the field that is wrong. Same
lesson as the `/stats` test in 6.11 §9.4: **a mocked persistence layer cannot pin a persistence
contract.**

### F8 — AC 16 is violated by the stub

`sendToDevice` logs the **full push token** to stdout. Push tokens are credentials for addressing a
device; they do not belong in logs.

## 3. Proposed scope split

### Phase 1 — deliverable and verifiable here (recommend doing this first)

Everything below runs against the real database and the real suite, no credentials required.

- **T1. Fix the `PushToken.playerId` contract (F1).** Decide what a push token is keyed to. The
  schema says `MvpPlayer`; the app is device-first and `MvpPlayer` is session-scoped, which is the
  same structural mismatch 6.8 hit with `TournamentFeedback`. Options in §4. This is a **blocker for
  everything else** and a schema decision, so it needs your call before code.
- **T2. Wire identity via Story 6.1 (AC 5).** `resolveIdentity(req)`; decide guest-token policy.
- **T3. Implement the transport (AC 2, F2).** Real `expo-server-sdk` send, replacing the stub.
  Testable without credentials by injecting a transport and asserting the payloads built.
- **T4. Honour `NotificationPreferences` (AC 3, F4).** Read preferences before send; suppress on
  opt-out. Fully testable.
- **T5. Resolve the two-implementations problem (F3).** Pick one access path. The service is richer
  (preferences, read-tracking, 10 domain senders) but unreachable; the route is reachable but thin.
- **T6. Stop logging tokens (AC 16, F8).**
- **T7. Replace the mock-based route test with a real-Postgres one (F7, AC 11)** — one that would
  have failed on F1.
- **T8. Correct the story text (F6)** so AC 6 does not name a private method as public API.

### Phase 2 — needs accounts, credentials, or production telemetry (not this environment)

- EAS build/submit profiles and a real store release (AC 1, 4, 13)
- Crash-free and opt-in measurement (AC 9, 10)
- Staged rollout mechanics (AC 12)
- Secrets provisioning in CI (AC 14) — depends on the `ci.yml` decision

Phase 2 should be tracked as its own workstream with an owner who has App Store Connect and Play
Console access. It cannot be "done" by an agent on this machine, and I would rather say so than
produce artefacts that look complete and are not.

## 4. The decision that gates everything: what is a push token keyed to?

`PushToken.playerId` → `MvpPlayer.id`, but `MvpPlayer` is **session-scoped** (`sessionId`
required) and `TournamentPlayer.userId` is NULL-by-design (Story 6.7 §D8). So a *player* is not a
stable identity across sessions, while a push token is exactly that — a durable device/account
handle.

Three options:

| Option | Change | Consequence |
|---|---|---|
| **A. Key to device** | `playerId` → nullable, add `deviceId` as the key; FK removed or repointed | Matches the device-first app and AC 5's "guest tokens where allowed". **Schema migration.** |
| **B. Key to account** | `playerId` → `User.id` | Matches logged-in users, breaks guests entirely — contradicts AC 5. |
| **C. Both** | nullable `userId` + nullable `deviceId`, at least one required | Most expressive, most work; mirrors how Story 6.7 handled tournament ownership (`organizerUserId` / `organizerDeviceId`). |

**I lean to C**, because 6.7 already established exactly this pattern for the same reason — a
device-first app where ownership must resolve from either a JWT or a device id — and reusing it
keeps the identity model coherent instead of inventing a third convention. But it is a schema
decision on a live table and it changes what "targeting" means, so it is yours to make.

**Until this is decided, T1–T5 are blocked.** T6–T8 are not, and I can do those immediately.

## 6. Open questions for the PO

1. **§4 — which identity model for push tokens?** Blocks T1–T5.
2. **Guest notifications:** AC 5 says "guest tokens where allowed". Which notification types may a
   guest receive? AC 16 forbids sensitive data, so presumably match/session reminders only.
3. **Is Phase 2 in scope for this story, or does it become its own release workstream?** Nine ACs
   cannot be closed here; a story that can never reach "Done" is worse than two honest ones.
4. **Does 6.9 wait for the `ci.yml` decision?** AC 14 assumes CI secrets exist, and CI currently
   does not run at all.
