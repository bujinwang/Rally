## 1. Headline findings

### F1 — ✅ FIXED (`8b645d6`): push token registration was impossible

Originally, `POST /notifications/register` wrote `playerId: deviceId`, but `PushToken.playerId` was a
**required FK to `MvpPlayer.id`**. Every call violated `push_tokens_playerId_fkey` (P2003) and the
route answered 500. A client could never register a token.

This is now fixed via **Option C** (§4):

- `PushToken.playerId` is **nullable and legacy** (`schema.prisma:1703`); no code path writes it.
- `PushToken.userId String?` was added with a FK to `User` and `onDelete: SetNull`
  (`schema.prisma:1713,1727`); `@@index([userId])` at `schema.prisma:1733`.
- `PushToken.deviceId` is unchanged (`schema.prisma:1708`).
- Migration `backend/prisma/migrations/20260917000000_story_6_9_push_token_identity/migration.sql`
  adds the column, the FK, the index, repoints `playerId`'s FK to `ON DELETE SET NULL`, and adds the
  CHECK `push_tokens_identity_present_check` (`migration.sql:44-46`).
- The route applies `optionalAuth` + `resolveIdentity(req)` and binds `userId`/`deviceId`, never
  `playerId` (`routes/notifications.ts:66-109`). Neither identity → **400 `VALIDATION_ERROR`**
  (`routes/notifications.ts:67-76`). The `deviceId` validator was relaxed to optional
  (`routes/notifications.ts:15`).
- The `findFirst({ where: { deviceId } })` null trap was fixed: an account-only caller looks up by
  `userId`, never a null `deviceId` (`routes/notifications.ts:81-83`).
- `routes/__tests__/notifications.test.ts` was rewritten to use the **real Postgres** (14/14 green).

**F1 is closed. Do not re-plan it.** See F9 for the consequence it did *not* resolve.

### F3 — there are THREE push implementations, and the "rich" one is not merely orphaned, it is schema-incompatible

The first draft framed this as two implementations. Recon for this pass found **three**, plus a
frontend orphan (F10):

| # | Module | Reachable? | Data access | State |
|---|---|---|---|---|
| 1 | `routes/notifications.ts` | **Yes** — mounted (`routes/index.ts:76`) | `prisma.pushToken` (client) | Correct + tested post-F1. Does **not** send. |
| 2 | `services/notificationService.ts` (599 lines, ~22 methods) | **No** — imported only by its own test (§8) | `prisma.$queryRaw` (raw SQL) | **Broken against the live schema** (below). |
| 3 | `utils/notificationHelper.ts` | **Yes** — 7 importers (§8) | `prisma.pushToken` (client) | Live send path; **mis-keyed** (F9); logs token prefixes (F8). |

The critical new fact about #2: **its raw SQL references columns that do not exist.** The service
queries `push_tokens` by `player_id`, `is_active`, `device_id`, `last_used` (`notificationService.ts:57,71-73,110-135`),
`notification_preferences` by `player_id`, `match_results`, `friend_requests`, … (`:166,225-244`) and
`notifications` by `player_id`, `is_read`, `read_at`, `delivered_at`, `sent_at` (`:26-40,281-293,321-341`).
But the live tables use **quoted camelCase** columns — verified directly against
`information_schema` (§8): `push_tokens` has `playerId/deviceId/isActive/lastUsed`, **no**
`player_id/is_active`; `notifications` has `playerId/isRead/readAt/deliveredAt/sentAt`, **no**
`player_id/is_read`; `notification_preferences` likewise. The migration file itself proves it:
`ALTER TABLE "public"."push_tokens" ALTER COLUMN "playerId" DROP NOT NULL;` (`migration.sql:28`).

So **every DB-touching method in the service would throw `column "player_id" does not exist` at
runtime.** It has never been executed against this schema. Its own test mocks `prisma.$queryRaw`
entirely (`services/__tests__/notificationService.test.ts:2-6`), which is why the incompatibility is
invisible to the suite — the same "a mocked persistence layer cannot pin a persistence contract"
lesson as F7.

**Therefore the premise of the original T5 ("the service is richer but unreachable") is false.** The
service is not richer; it is *broken*. There is no valuable raw-SQL token storage to preserve — it
cannot run. The 10 `NotificationHelpers` senders (`:444-603`) are thin wrappers over
`sendNotification`, which is itself broken → they are dead weight too (unreachable **and**
non-functional). See §5 for the decision this forces.

### F9 — 🆕 BLOCKER for AC 2: registration and delivery are keyed on **different columns**

The F1 fix made registration write `userId`/`deviceId` and **stop writing `playerId`**. But the live
send path still reads by `playerId`:

```ts
// utils/notificationHelper.ts:46-50   (notifySessionSubscribers)
const tokens = await prisma.pushToken.findMany({ where: { playerId: player.id } });
// :83-85    (notifyDevice — parameter is `userId`, but it queries `playerId`)
const tokens = await prisma.pushToken.findMany({ where: { playerId: userId } });
// :116-118  (notifyPlayer) — same
```

Post-F1, `playerId` is always NULL. So **every token registered through the route is invisible to
every sender**: a device registers successfully (200) and then receives **nothing**. AC 2 ("push
end-to-end") is not met — the two halves of the pipeline are wired to different keys.

Worse, `notifyDevice(userId, …)` is called with a **`User.id`** from four live sites —
`scheduler.ts:243` (`reminder.userId`), `friends.ts:62` (`receiverId`) and `:119`
(`response.senderId`), `messaging.ts:113` (`recipientId`) — and queries it against `playerId`. That
is the *same identity-confusion defect class as Story 6.8's D5* (`TournamentFeedback.playerId` held a
`User.id`), except here it is a `WHERE` clause rather than an FK, so there is no P2003 — just silent
zero rows. **This is the defect the next implementation pass must fix**, and it is why T3 (transport)
cannot be done in isolation: a real transport sending to zero tokens changes nothing observable.

## 4. The identity decision — ✅ RESOLVED (Option C)

`PushToken.playerId` → `MvpPlayer.id`, but `MvpPlayer` is **session-scoped** (`sessionId` required,
`schema.prisma:242`) and `MvpPlayer.userId` is NULL-by-design for guests (`schema.prisma:249`). So a
*player* is not a stable identity across sessions, while a push token is exactly that — a durable
device/account handle.

Of the three options in the prior draft (A key-to-device, B key-to-account, C both), **Option C was
chosen and committed** (`8b645d6`): a token is keyed to a **user and/or a device, at least one
required**, enforced by the DB CHECK `push_tokens_identity_present_check`. Rationale (from the
migration's own header, `migration.sql:8-12`): it mirrors Story 6.7's tournament-ownership pattern
(`organizerUserId`/`organizerDeviceId`) for the same reason — a device-first app where identity must
resolve from either a JWT or a device id — and it is a strict superset of "key to device", so it
serves guests *and* account holders as AC 5 requires.

**This closes open question #1 from the prior draft. No further identity decision is pending.** The
one remaining identity-adjacent open item is the *guest allow-list* (Q2), which is policy, not schema.

## 5. T5 — the decision: retire `services/notificationService.ts`, consolidate on the route + the live helper

The prior T5 asked which of two access paths to keep. Recon for this pass shows there are **three**
(F3) and that the framing was wrong: the "richer" service is **broken against the live schema**, so
"make the route delegate to the service" would import dead code into the live path. Decision:

> **Retire `services/notificationService.ts` entirely. Keep `routes/notifications.ts` (correct,
> tested, Option-C token storage). Make `utils/notificationHelper.ts` the single send path, re-keyed
> on `userId`/`deviceId` (F9) and given a real transport (T3) and preference gating (T4). Port only
> the three *pure* helpers from the service.**

### Justification

1. **The service cannot run, so it has nothing to offer as a whole.** Every DB query in it names a
   column that does not exist (F3, verified against `information_schema`). "Delegate to the service"
   is not a refactor; it is a rewrite, and the result would be a *worse* starting point than the route
   (which is already correct and tested).
2. **The route holds the one piece that was just fixed and verified.** Its Prisma-client, Option-C
   token storage passed 14 real-DB tests. Deleting it would throw that away and force its re-derivation
   from a raw-SQL implementation that does not work.
3. **The live fan-out point is `utils/notificationHelper.ts`, not the route.** The route *registers*
   tokens; it never *sends*. Seven modules already call the helper (§8): `scheduler.ts`,
   `mvpSessions.ts` (×2), `scoring.ts`, `pairings.ts`, `friends.ts`, `messaging.ts`,
   `socket/notificationHandlers.ts`. Putting the transport (T3) and gating (T4) **there** makes all
   seven gain real delivery in one change. Wiring the route would send nothing.
4. **Retiring the service is safe — nothing imports it.** Verified by grep across `backend/src` and
   `frontend`: the only importer is `services/__tests__/notificationService.test.ts` (§8). Removing
   both files cannot break any caller.

### What happens to each piece of the service

| Piece | Lines | Disposition |
|---|---|---|
| `sendToDevice` stub | `:85-101` | **Deleted.** Replaced by the real transport (T3). |
| Raw-SQL token storage (`registerPushToken`, `unregisterPushToken`) | `:106-158` | **Deleted, not migrated.** It writes to columns that do not exist; the route's Prisma-client storage is the survivor. |
| Preferences CRUD (`get/updateNotificationPreferences`) | `:163-267` | **Deleted.** Replaced by a small Prisma-client `notificationPreferences.ts` (T4). |
| Notifications CRUD (`getNotifications`, mark-read ×2, unread-count, cleanup) | `:272-381` | **Deleted.** No route exposes them and no caller exists — dead. |
| `isNotificationEnabled`, `isInQuietHours`, `parseTimeString` | `:386-440` | **Ported** (pure functions — the only genuinely reusable part). See T4. |
| 10 `NotificationHelpers` senders | `:444-603` | **Deleted.** Unreachable **and** non-functional (they call the broken `sendNotification`). Confirmed dead weight, not "rich". |
| `sendPushNotification` (`private`) | `:52-80` | **Deleted.** Its role moves to the helper + transport. |

### Consequence for T3 and T4 (where they live)

- **T3 lives in a new `backend/src/services/pushTransport.ts`**, consumed by
  `utils/notificationHelper.ts`. It does **not** live in the deleted service.
- **T4 lives in a new `backend/src/services/notificationPreferences.ts`** plus a small

- **T5's deletion happens first** (step 1 of §6), so T3/T4 are never written against the broken file.

## 6. Implementation spec — T3, T4, T5

### T3 — real push transport (AC 2, F2)

**Goal:** replace the stub with a real `expo-server-sdk` send, testable with **no Expo credentials**,
that also unblocks delivery (with F9).

**New file:** `backend/src/services/pushTransport.ts`

**Seam for testing without credentials:** the SDK client is **constructor-injected**. Tests pass a
fake client (or a fake `PushTransport`); production constructs the real `Expo`. No token, no network,
no credentials in any test.

```ts
import { Expo } from 'expo-server-sdk';

export interface PushMessage {
  to: string;                          // Expo push token
  title: string;
  body: string;
  data?: Record<string, unknown>;
  sound?: 'default' | null;
  priority?: 'default' | 'normal' | 'high';
}

export type PushTicketError =
  | 'DeviceNotRegistered' | 'InvalidCredentials' | 'MessageTooBig'
  | 'MessageRateExceeded' | 'ProviderError' | 'DeveloperError' | 'ExpoError';

export interface PushTicket {
  token: string;                       // echoed for index-safe correlation
  status: 'ok' | 'error';
  error?: PushTicketError;
  message?: string;
}

export interface PushTransport {
  send(messages: PushMessage[]): Promise<PushTicket[]>;
}

/** Minimal shape we depend on, so tests can fake the SDK. */
export interface ExpoClientLike {
  chunkPushNotifications(m: any[]): any[][];
  sendPushNotificationsAsync(m: any[]): Promise<any[]>;
}

export class ExpoPushTransport implements PushTransport {
  constructor(private readonly client: ExpoClientLike = new Expo({
    accessToken: process.env.EXPO_ACCESS_TOKEN,   // undefined is fine for public Expo push
    useFcmV1: true,
  })) {}

  async send(messages: PushMessage[]): Promise<PushTicket[]> { /* chunk → send → map, see below */ }
}
```

**Behaviour the spec fixes** (verified against the installed `expo-server-sdk@3.15.0` typings,
`build/ExpoClient.d.ts`):

- **Payload construction.** Each `PushMessage` → `{ to, title, body, data, sound: 'default',
  priority: 'high' }`. `ExpoPushMessage.to` may be a single token; we send one message per token so
  tickets map 1:1 to tokens (`ExpoClient.d.ts:56-80`).
- **Batching.** Use `client.chunkPushNotifications(...)` (limit 100,
  `ExpoClientValues.d.ts:7`) and call `sendPushNotificationsAsync` once per chunk. Never send an
  unbounded array.
- **Index-safe correlation.** `sendPushNotificationsAsync` returns tickets aligned to the input
  array (`ExpoClient.d.ts:16-26`). Map each ticket back to its token by index and **echo the token**
  on the returned `PushTicket`, so callers never re-derive it.
- **Skip non-Expo tokens.** Before sending, filter with `Expo.isExpoPushToken(token)`
  (`ExpoClient.d.ts:14`); a token that fails is returned as a `DeveloperError` ticket and is
  **deactivated** (same path as `DeviceNotRegistered`).
- **Per-token error isolation.** One error ticket must not abort the batch; other tokens still send.
- **`DeviceNotRegistered` handling.** For any returned ticket with `status: 'error'` and
  `details.error === 'DeviceNotRegistered'` (`ExpoClient.d.ts:93-101`), **deactivate the token row**:
  `prisma.pushToken.updateMany({ where: { token }, data: { isActive: false } })`. This is the prune
  contract and it **requires a test** (below).
- **Transport failure.** If `sendPushNotificationsAsync` rejects (network/timeout), catch it and
  return error tickets for that chunk — never throw into the caller's fire-and-forget sites.
- **Redaction (F8).** Never log the full token; log at most the existing 4-char mask.

**Receipts (call out explicitly):** Expo delivers `DeviceNotRegistered` reliably via **receipts**
(`getPushNotificationReceiptsAsync`, `ExpoClient.d.ts:27-29`), not always in the immediate ticket.
Full receipt handling needs a scheduler job and receipt-id persistence. **Recommendation:** implement
the immediate-ticket prune in T3 (testable now), and file receipt polling as a **Phase-1.5** task —
it is testable with a fake client but is a scheduling/state addition beyond AC 2's "wired" bar.

**Consumer change (also fixes F9):** `utils/notificationHelper.ts` builds `PushMessage[]` from the
tokens it finds and calls `transport.send(...)`, replacing the `console.log` placeholders at `:58`
and `:91`.

**Tests** — `backend/src/services/__tests__/pushTransport.test.ts` (fake client, no credentials):

## 11. Ruling — F11: `NotificationPreferences` is the authoritative store for push consent

**Decision.** `notification_preferences` is the **single authoritative store for push consent**. The
UI is repointed to it. The gate stays where it is.

**Rationale.**

1. **The gate already reads it, and only it.** `isDeliverable` (`notificationHelper.ts:118-131`) →
   `loadPreferences` (`:95-106`) reads `prisma.notificationPreferences`. Phase 1 made this the single
   source of truth; moving the gate to `user_settings` would mean *rewriting the thing we just
   verified*.
2. **Only `notification_preferences` has the columns the gate needs.** The policy needs `pushEnabled`
   (master), `challenges`, `tournamentUpdates`, `socialMessages`, `quietHoursStart/End` — **none** of
   which exist on `user_settings` (`schema.prisma:775-780`). Repointing the gate would require adding
   five columns to `user_settings` and re-deriving the whole preference model. The asymmetry is
   decisive: the UI can be moved cheaply; the gate cannot.
3. **The consumer must satisfy the producer, not vice versa.** Consent is a promise about what the
   *sender* does. The sender is the gate. Therefore the store the gate reads is authoritative by
   construction.

**Disposition of the losing store's columns**
(`user_settings.friendRequests/messages/sessionInvites/matchResults/achievements`): **deprecate, keep,
remove later — do NOT repoint.**

- They remain for now because `GET/PUT /users/:userId/settings` (`routes/users.ts:377-508`) still
  read/write them, and removing them is a destructive change to a live table.
- **Writer map (reconciled with QA, task #55):** the only **live** writer/reader of these columns is
  `routes/users.ts:473` (+ `:377-440`). `services/userService.ts:186` (create) and `:229` (upsert)
  also write them, but `UserService` has **zero production importers** — only its own test imports it
  (`services/__tests__/userService.test.ts`) — so those are **dead-code writes**. Footnote for the
  cleanup (T13): if `UserService` is ever wired up, it would silently resurrect a second writer; the
  T13 migration must account for it. For `notification_preferences` the trace is unambiguous — the
  **only** writer anywhere is `routes/notifications.ts:322,327` (upsert).
- Mark them **deprecated / not consulted for push consent** (comment in `schema.prisma` + the route).
- Remove them in a **separate follow-up migration** once nothing reads them (i.e. after the UI stops
  sending `notificationSettings`). That keeps the destructive step revertible and out of this fix.

**Field mapping the UI must use** (the five existing switches + the master toggle):

| UI label | `notification_preferences` field | Notes |
|---|---|---|
| Friend Requests | `friendRequests` | unchanged |
| Messages | `socialMessages` | **re-map** (was `messages`) |
| Session Invites | `sessionReminders` | **re-map** (was `sessionInvites`) |
| Match Results | `matchResults` | |
| Achievements | `achievements` | |
| **Master push toggle (ADD)** | `pushEnabled` | currently unreachable from any UI; `false` suppresses **all** pushes |

Recommended (not required) additions for AC 3 completeness: `challenges`, `tournamentUpdates`, and
quiet hours — the gate honours them but no UI can set them today.

**Which story.** **This one (Phase 1).** AC 3 is already a Phase-1 AC and this *is* its opt-out path;
shipping a "Settings saved" that silently does not honour opt-out would be worse than not claiming
AC 3. Scope it tightly: repoint the UI + map fields + surface the master toggle. The `user_settings`
column removal is a **follow-up** (task T13, not this story).

## 12. Ruling — F12: one preferences-only client; delete the orphan

**Decision.** **Delete `notificationApi.ts`.** Add **one** focused API client,
`frontend/Rally/src/services/notificationPreferencesApi.ts`, that reads/writes
`/notifications/preferences` and nothing else. Do **not** extend `NotificationService.ts`.

**Rationale.**

1. **The preferences client is an *API client*, not a *device service*.** `NotificationService.ts` is a
   device-side Expo singleton (permissions, listeners, token acquisition); it makes a bare
   unauthenticated `fetch` for registration. Preferences are identity-scoped (the endpoint runs
   `resolveIdentity`) and belong to the authenticated API layer, alongside `userApi.ts`.
2. **A new client follows the *tested* pattern directly.** The codebase already pins API clients with
   `src/services/__tests__/apiService.consumers.test.ts` (real `http` server, byte-exact backend
   bodies, mocked `authFetch` + `config/api`). A preferences client using `getAuthHeaders()`
   (the `userApi.ts:65-71` pattern) drops straight into that harness. Adding authenticated CRUD to the
   device singleton would not.
3. **It mirrors the *spirit* of the backend T5 decision — one path, no orphans.** The backend's "live
   path" was the *sender* (`notificationHelper`); the frontend has **no** live preferences client, so
   we create exactly one. `NotificationService.ts` keeps its (correct) token role.
4. **Naming honesty.** `notificationApi.ts` implies a full notification API; after the reduction it is
   preferences-only, so the name should match its scope. (If the engineer prefers minimal churn,
   keeping the filename and reducing it in place is an acceptable equivalent — the outcome is one
   preferences-only client either way.)

**Disposition of the four nonexistent inbox methods** (`getNotifications`, `markNotificationAsRead`,
`markAllNotificationsAsRead`, `getUnreadNotificationCount`): **delete.** The backend has never served
an inbox; an in-app inbox is out of 6.9's scope (AC 2 = delivery, AC 3 = consent). Do not carry dead
client methods for endpoints that do not exist. If an inbox is wanted, it is a new feature with its own
backend endpoints — not a passenger in this fix.

**Disposition of the token methods** (`registerPushToken`/`unregisterPushToken` in `notificationApi.ts`):
**delete.** The live `NotificationService.ts` already owns token registration correctly (F12), and the
orphan's versions are contract-wrong.

**Registration consolidation (F13).** Because a **third** live registration path exists (the inline
fetch in `useNotificationManager.ts:68`, F13), "delete the orphan's token methods" is necessary but not
sufficient. The hook must stop re-implementing registration and **delegate to
`NotificationService.registerPushToken`** (which is the live, correct path). See T14 in §13.

**Confirmation from QA's inventory (task #55):** there is **no live caller** of any inbox-style
endpoint — the six never-exposed paths live only in the orphan — so "drop the inbox methods" is safe.
QA also found that **three live backend notification routes have zero live frontend callers**:
`DELETE /notifications/register/:deviceId` (the only `unregisterPushToken` reference is the orphan),
`DELETE /:shareCode/unsubscribe` (`NotificationService.unsubscribeFromSession` is defined at `:277` but
never invoked), and `GET /:shareCode/subscribers` (no frontend reference). Only `POST /register` and
`POST /:shareCode/subscribe` (`JoinSessionScreen.tsx:115`) have live callers. These are dead backend
surfaces, not defects — recorded for the cleanup follow-up (T13), not actioned here.

**Reachability (anti-orphan — a new module must not become the 4th/5th orphan).** The new
`notificationPreferencesApi.ts` is imported by **`SettingsScreen.tsx`**, which is reachable: `Settings`
is registered in `ProfileStack` (`navigation/MainTabNavigator.tsx:263-264`) and reached from
`screens/UserProfileScreen.tsx:60` (`navigation.navigate('Settings', { userId })`). The client is
proven by a consumer test (§13 T11), so it cannot silently drift from the backend again.
