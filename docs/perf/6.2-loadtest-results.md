satisfying AC 9 (p95 < 200 ms, p99 < 500 ms), AC 10 (cache hit rate > 80%) and
AC 11 (script + thresholds committed).

## How to run

```bash
# 1. Start the backend (the load test hits a *running* server).
cd backend
PORT=3999 RATE_LIMIT_MAX_REQUESTS=10000000 RATE_LIMIT_WINDOW_MS=1000 npm run dev

# 2. In another shell, run the load test.
BASE_URL=http://localhost:3999 CONNECTIONS=50 DURATION=10 node src/scripts/loadtest.mjs
# or: npm run loadtest
```

- `autocannon` is declared as an optional devDependency; when it is not
  installed the script transparently uses a dependency-free `node:http` runner
  with fixed concurrency (used for the snapshot below).
- The global `/api/` rate limiter must be raised for the run (see the command
  above). The per-route limiters on discovery/analytics (60 req / 15 min) are
  not env-configurable, so the load test targets cached read paths **without** a
  per-route limiter: `GET /api/v1/mvp-sessions` (cached under the `discovery`
  domain), `GET /api/v1/health`, `GET /api/v1/health/cache`.
- This step is **manual / CI-optional** and is intentionally **not** part of
  `npm test` (which stays green and Redis-free).

### Environment

- Local developer machine (macOS), Node.js, PostgreSQL running locally.
- **Redis was NOT reachable** in this environment (port 6379 closed), so the
  cache ran on the in-memory store via the graceful-fallback path. This is a
  valid exercise of the cache layer + invalidation, but the numbers reflect the
  memory driver, not Redis. Re-run in staging/production (with `REDIS_URL`
  pointing at a live Redis) to capture Redis-backed numbers.
- `X-Cache` behaviour verified separately: the first `GET /api/v1/mvp-sessions`
  returned `X-Cache: MISS`, the second `X-Cache: HIT`.
