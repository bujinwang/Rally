# Story 6.2 — Caching: keys, TTLs, invalidation & indexes

Reference for the Redis-backed cache (`backend/src/services/cacheService.ts`) and
its storage drivers (`MemoryStore`, `RedisStore`). Source of truth for TTLs and
key builders is `backend/src/services/cache/cacheKeys.ts`.

## 1. Architecture

```
CacheService  ──delegates──▶  CacheStore (interface)
                                   ├── MemoryStore  (Map + TTL + LRU + max-entry cap)
                                   └── RedisStore   (redis client + circuit breaker)
```

- **Store selection:** `RedisStore` is used only when `REDIS_URL` is set;
  otherwise `MemoryStore` (dev/test default).
- **Best-effort (AC 14):** a read error is treated as a cache miss; a write error
  is logged and swallowed. Redis being down **never** produces a 5xx. When the
  primary store errors, the service serves from the in-memory fallback.
- **Circuit breaker:** after 5 consecutive Redis failures the breaker opens for
  30 s and commands fail fast (no socket I/O); it probes again after the window.

## 2. Key schema (AC 16 — no PII)

All keys are namespaced with `REDIS_KEY_PREFIX` (default `rally:cache:`). The
variable part of every key is **SHA-1 hashed**, so raw user input, email, phone
numbers or free-text never appear in a key.

| Purpose | Key pattern | TTL |
|---------|-------------|-----|
| Discovery list | `rally:cache:discovery:g<gen>:<sha1(filters+loc)>` | 300 s |
| Nearby | `rally:cache:nearby:g<gen>:<sha1(lat,lon,radius)>` | 300 s |
| Session detail | `rally:cache:session:g<gen>:<sessionId>` | 600 s |
| Popular sessions | `rally:cache:popular:g<gen>:sessions` | 900 s |
| Location | `rally:cache:location:g<gen>:<lat2>:<lon2>:<radius>` | 1800 s |
| Stats / general | `rally:cache:stats:g<gen>:general` | 3600 s |
| Analytics leaderboard | `rally:cache:analytics:g<gen>:leaderboard:<limit>` | 300 s |
| HTTP (middleware) | `rally:cache:<domain>:g<gen>:http:<METHOD>:<path>:<sha1(query)>` | 300 s (per-route) |
| Generation counter | `rally:cache:gen:<domain>` | none (persistent) |

`<sessionId>` is a cuid (not PII). Coordinates are rounded to 2 dp before
hashing. HTTP middleware keys embed **no identity** for public reads (assumption A5).

## 3. Invalidation (AC 2, 8, 12) — generation counters, never `KEYS`/`SCAN`

- Each domain owns a counter at `rally:cache:gen:<domain>`.
- Keys embed the current generation (`g<gen>`).
- **Invalidate = `INCR rally:cache:gen:<domain>`.** O(1) and atomic; previously
  cached keys become unreachable and age out via their TTL.
- Invalidation runs **fire-and-forget after a 2xx DB commit**; a write never
  depends on cache success (AC 8). A missed bump can at worst serve a stale read
  until the short TTL expires.

### Domain invalidation map

| Write route | Bumps generations |
|-------------|-------------------|
| `POST /mvp-sessions` (create) | `session`, `discovery`, `stats` |
| `PUT /mvp-sessions/:shareCode` (edit) | `session`, `discovery` |
| `PUT /terminate/:shareCode`, `PUT /reactivate/:shareCode` | `session`, `discovery`, `stats` |
| `POST /join/:shareCode`, `DELETE /:shareCode/leave-by-device` | `session`, `discovery` |
| `DELETE /:shareCode/players/:playerId`, `POST /:shareCode/add-player` | `session`, `discovery` |
| player status / check-in / check-out / rest | `session` |
| `POST /analytics/refresh/*` | `stats`, `analytics` |
| `POST /sessions/discovery/:sessionId/join` | `session`, `discovery` |

## 4. Memory bounds (AC 15)

- `MemoryStore` keeps the 256 MB cap (constructor default) with LRU eviction
  under pressure, plus a periodic (5 min, `unref()`'d) expiry sweep.
- Every store enforces `CACHE_MAX_ENTRY_BYTES` (default 262144 = 256 KB):
  oversized values are **skipped** (not cached) and logged at debug level.
- Recommended Redis server policy (assumption A2, not client-enforceable):
  `maxmemory-policy allkeys-lru`.

## 5. Configuration (AC 13 — env only, no hardcoded hosts)

| Var | Default | Purpose |
|-----|---------|---------|
| `REDIS_URL` | _(unset)_ | Redis connection string; absent ⇒ memory store |
| `REDIS_KEY_PREFIX` | `rally:cache:` | Key namespace |
| `CACHE_MAX_ENTRY_BYTES` | `262144` | Max size of a single entry (bytes) |
| `REDIS_CONNECT_TIMEOUT_MS` | `5000` | Client connect timeout |
| `REDIS_MAX_RETRIES` | `10` | Max reconnect backoff exponent (delay capped at 5 s) |

## 6. Query profiling & indexes (AC 4)

Prisma query logging (`log: ['query']`) plus `EXPLAIN ANALYZE` on the hot queries
identified two index gaps that are justified by static analysis of the query
shape (no live Postgres was available in the build environment to capture a
before/after plan — see the note below):

1. **`MvpSession.ownerDeviceId`** — `GET /mvp-sessions/my-sessions/:deviceId`
   filters `ownerDeviceId = :deviceId AND status = 'ACTIVE'`, ordered by
   `createdAt desc`. Before: sequential scan on `mvp_sessions`. Added:
   `mvp_sessions_ownerDeviceId_idx` and the composite
   `mvp_sessions_ownerDeviceId_status_idx` (both equality predicates).
2. **`MvpPlayer.deviceId`** — device-only lookups (guest joins, `POST /auth/claim`,
   device permission checks) had only the `@@unique([sessionId, deviceId])`
   prefix. Added: `mvp_players_deviceId_idx`.

The migration `prisma/migrations/20260912000000_story_6_2_perf_indexes/migration.sql`
is **additive** (indexes only) and **reversible** (`DROP INDEX` block included).

**Correction (post-QA, F1):** an earlier revision used `CREATE INDEX CONCURRENTLY`,
which **cannot run inside a transaction block** (PostgreSQL 25001). Prisma Migrate
wraps every migration file in a transaction, so `prisma migrate deploy` failed with
P3018. The migration now uses plain `CREATE INDEX IF NOT EXISTS`, which is fully
compatible with Prisma's transactional runner and applied atomically with the
migration record. (If a genuinely huge production table ever needs a non-blocking
build, do it as a separate, explicitly non-transactional operation — never by
putting `CONCURRENTLY` inside this file.)

**EXPLAIN note:** this environment had no reachable PostgreSQL instance, so the
plan output could not be captured here. On a populated database, re-run:

```sql
EXPLAIN ANALYZE
SELECT * FROM mvp_sessions
WHERE "ownerDeviceId" = '<deviceId>' AND status = 'ACTIVE'
ORDER BY "createdAt" DESC;
```

and confirm the plan switches from `Seq Scan` to `Index Scan` /
`Index Scan Backward` using `mvp_sessions_ownerDeviceId_status_idx`.

### Deferred / future optimizations (assumption A3)

- Discovery free-text search uses `contains` (ILIKE) and is not index-friendly
  without the `pg_trgm` extension. A trigram index is intentionally **not** added
  in 6.2 (extension availability is not guaranteed) and is noted as a future item.
- Composite discovery indexes (`[status, visibility, skillLevel]` /
  `[status, visibility, courtType]`) are candidate optimizations to add only when
  an `EXPLAIN` plan on production data justifies them.

## 7. Observability

- `CacheService.getCacheStats()` → `{ hits, misses, hitRate, driver, entries, memoryUsageMB }`.
  (Named `getCacheStats()` — not `getStats()` — because `getStats()` already
  returns the *stats-domain data*. See the naming note in `cacheService.ts`.)
- `GET /api/v1/health/cache` exposes the store health + metrics for monitoring
  (Story 6.3).
- The HTTP middleware adds an `X-Cache: HIT|MISS` response header.
